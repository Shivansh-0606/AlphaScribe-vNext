## Purpose

Define the **routing strategy** for the Next.js 15 App Router: the philosophy, the route-grouping model,
how nested layouts attach to routes, who owns route content, URL-design principles, and route boundaries.
This is routing **architecture** — it **does not define individual pages** (Constitution §2, §7).

## Scope

**In scope:** App Router philosophy, route grouping, nested layouts (routing view), route ownership, URL
principles, route boundaries. **Out of scope:** designing routes/pages, redesigning navigation or IA
(frozen), implementation.

## Architectural Decisions

### AD-1 — App Router philosophy: thin routes, server-first, navigation-faithful
- **Routes are thin compositions**, not logic: a route segment composes a layout + feature UI and owns no
  business logic (that lives in the feature/application layers — §4.5, [02.2](02.2_Feature_Organization.md)).
- **Server-first** (§7): route segments render on the server by default; interactivity is delegated to
  client islands within them ([02.6](02.6_UI_Layer_Architecture.md)).
- **Routes realize the frozen [Navigation Structure](../design/04_Navigation_Structure.md) exactly** —
  every destination maps to an existing IA domain/level; **no new destinations** are introduced by routing.

### AD-2 — Route grouping mirrors the frozen layout-template families
Routes are grouped by **access context / shell family**, matching the five frozen
[layout templates](../design/09_Component_Inventory.md#templates). Grouping organizes shared layout +
access rules without affecting the URL's meaning:

| Route group (by shell/access) | Frozen template | Frozen destinations it hosts (IA/Nav) |
|-------------------------------|-----------------|----------------------------------------|
| Public | PublicTemplate | Landing, Authentication |
| Setup | SetupTemplate | Onboarding & AI Setup (global nav suppressed) |
| Workspace | WorkspaceTemplate | Workspace Home, Search, Research Library, Settings |
| Research | ResearchTemplate | Company Research, Comparison, Learning (+ section nav + AI companion) |
| Document | DocumentTemplate | Report Viewer |

Grouping is an **organizational** device (shared layout + access boundary), not a URL-visible segment
where that would leak structure; the **destinations and hierarchy remain exactly the frozen ones**.

### AD-3 — Nested layouts follow the frozen layout hierarchy
Route nesting attaches the **persistent → template → feature** layout chain defined in
[02.4](02.4_Layout_Architecture.md): a root shell wraps all routes; a template layout wraps its group; a
feature (e.g. Company Research) may nest a section-level layout (section nav + companion). Persistent
layouts are **preserved across navigation** (Next.js App Router), which structurally supports continuity
and **never-lose-work** (§6.3).

### AD-4 — Route ownership
- The **app shell / root layout** owns global chrome (header, global navigation, providers, landmarks,
  skip link) — Architecture-defined, Engineering-built.
- **Each feature owns the content of its routes** (via its public UI surface — §4.12); routes do not reach
  into feature internals.
- **Access/auth boundaries** are owned by the routing layer (AD-6), not scattered into features.

### AD-5 — URL design principles
- **Research-first and stable:** URLs are organized around the **company as the primary unit of research**
  (frozen IA Search & Discovery), and are **stable and shareable** so a research subject/session can be
  returned to (recall over reconstruction; supports Resume Session — J-06).
- **Faithful to the IA hierarchy:** a URL reflects the frozen content hierarchy (e.g. company → level)
  where hierarchy exists; it never implies a structure the IA does not define.
- **Human-readable and predictable** (§4.10 explicitness): meaningful, lowercase, hyphenated segments; the
  same intent always yields the same URL.
- **Privacy-preserving (mandatory):** **no sensitive or personal data in URLs/query strings** — only
  non-sensitive identifiers/state. (Aligns with the platform privacy rules.)
- **No new vocabulary:** URL terms use frozen product vocabulary; routing coins no synonyms (§Design
  Constitution §15).

### AD-6 — Route boundaries
- **The login wall is a routing boundary:** all protected destinations sit behind an authentication
  boundary; unauthenticated access resolves to the frozen **Authentication Required** state and preserves
  the intended destination (frozen [States](../design/13_States.md#authentication-required)).
- **AI-access boundary:** destinations requiring validated AI access resolve to **Permission Denied** with
  a recoverable path to AI setup (frozen States), rather than a hard stop.
- **Segment boundaries** align with feature boundaries — a route segment is owned by exactly one feature.
- **Error/loading boundaries** exist per segment so a failure is scoped and recoverable (fail-fast for the
  unexpected, graceful frozen States for the expected — §4.13); navigation always remains available
  (frozen Navigation States).

## Design Rationale

A thin, server-first, navigation-faithful routing layer keeps routes free of logic (maintainability,
§4.5), preserves the frozen navigation/IA exactly (no scope drift), and leverages App Router's persistent
layouts to deliver continuity and never-lose-work structurally rather than by ad-hoc effort. Grouping by
shell family reuses the five approved templates and centralizes access rules at the boundary where they
belong.

## Alternatives Considered

- **Logic-bearing route handlers** (data/business logic in routes) — rejected: couples routing to
  behavior, harms cohesion (contra §4.5); logic stays in feature/application layers.
- **Client-side routing SPA** — rejected: forfeits server-first performance/SEO benefits (contra §7).
- **URL structure diverging from IA for convenience** — rejected: URLs must reflect the frozen structure;
  divergence confuses and risks scope drift.

## Trade-offs

- **Server-first routing vs. instant client transitions:** server segments add a round-trip for some
  navigations; mitigated by App Router streaming/prefetching and client islands (§7). Accepted for the
  performance/SEO/faithfulness benefits.
- **Grouping abstraction vs. simplicity:** route groups add a layer of organization; justified by shared
  layout + centralized access rules.

## Risks

- **Route sprawl / inconsistent URLs** as screens grow. *Mitigation:* URL principles (AD-5) + review;
  routes map 1:1 to frozen destinations only.
- **Access-boundary leakage** (a protected surface reachable unauthenticated). *Mitigation:* auth as a
  routing boundary (AD-6), verified in QA; never-lose-intent on redirect.
- **Logic creeping into routes.** *Mitigation:* thin-route rule (AD-1) enforced in review.

## Future Extension Points

- New destinations (future roadmap) attach as new route segments within the appropriate shell group — no
  change to existing routes (§4.14).
- Additional access tiers (should the roadmap introduce them via CR) extend the routing boundary model.
- Internationalized or additional public/SEO surfaces attach at the public group without disturbing
  authenticated routes.
