## Purpose

Define the **component architecture**: the component taxonomy (layering), who owns each layer, the
composition philosophy, the reusable-component strategy, and the separation between presentational and
feature-specific components. It **architects** the component system built from the frozen design system; it
**implements no components** (Constitution §2).

## Scope

**In scope:** component taxonomy, ownership, composition philosophy, reuse strategy, presentational vs.
feature-specific separation. **Out of scope:** implementing components, redefining the frozen component
specs/tokens, styling detail.

## Architectural Decisions

### AD-1 — A layered component taxonomy (from the frozen handoff)
Components are organized in a strict **layering** that matches the frozen M3 handoff, from most generic to
most specific. Each layer may compose only lower layers.

```
1. Primitives            wrapped shadcn/ui primitives bound to tokens + a11y (never used raw)
2. Foundation components Families 01–07 (Button, Input, Card, Table, Overlays, Feedback, …)
3. AI components         Family 08 (Prompt Composer, Streaming, Citations, Companion, …)
4. Research components    Family 09 (MetricStat, StatementTable, ChartFigure, FilingViewer, …)
5. Feature components     feature-specific compositions wired to feature state/data (per feature)
6. Screen compositions    a screen assembled from layouts + the above (no NEW components — frozen M2 rule)
   (Layout components — the shell/template/section layouts — are defined in 02.4)
```

**Direction of composition is one-way upward** (a lower layer never imports a higher one — §4.12,
[02.7](02.7_Module_Dependency_Rules.md)).

### AD-2 — Component ownership (three departments; §6.5)
| Concern | Owner |
|---------|-------|
| A component's **visual/interaction spec + tokens** | **Design** (frozen; CR to change) |
| The component's **layer, boundary, public interface, composition rules** | **Frontend Architecture** |
| The component's **implementation, optimization, tests** | **Frontend Engineering** |

Architecture never changes a component's design; Engineering never invents a variant/state not in the
design (frozen Component Mapping/Specs).

### AD-3 — Composition over inheritance; wrap, don't consume raw
- **Composition over inheritance** (§4.4): components are assembled from smaller components; there is no
  base-class hierarchy. Shared behavior is composed in.
- **Wrap primitives, don't consume them raw** (frozen handoff): each shadcn primitive is wrapped by an
  AlphaScribe component that binds tokens, states, and accessibility; **screens/features never import
  shadcn primitives directly**. This localizes a future primitive swap to one wrapper (§4.14).

### AD-4 — Stable public interfaces (props as contracts)
Each component exposes a **small, deliberate public interface** whose variant/size/state vocabulary matches
the frozen design and the [Component Mapping](../experience_design/engineering_handoff/12_Component_Mapping.md)
**1:1** (§4.12). A component's internals are private. An interface change is an ADR/CR event, not an ad-hoc
edit.

### AD-5 — Presentational vs. feature-specific separation
- **Presentational components** (layers 1–4) are **pure**: they render from props, hold no feature/business
  logic, do not fetch or own server state, and are reusable across features. They are the design system.
- **Feature-specific components** (layer 5) **wire** presentational components to a feature's state/data
  (via the application layer) and behavior; they live inside their feature module.
- The seam between them is the mechanism of reuse and low coupling (§4.3, §4.5): data/behavior flows down
  as props; presentational components stay context-free.

### AD-6 — Reusable-component strategy & promotion path
- **Reusable = presentational + feature-agnostic**; these live in the shared design-system layer.
- **Feature-specific stays in its feature** until a *proven, repeated* cross-feature need justifies
  promotion (§4.11 — avoid premature generalization).
- **Promotion is governed:** feature → shared requires review (it becomes a system-wide contract) and,
  if it introduces a new design pattern, a **design CR** (§6.5). New generic components enter with their
  full frozen attribute set or not at all (governance rule).

## Design Rationale

A strict, one-way component layering that mirrors the frozen handoff gives the system a predictable shape,
makes reuse obvious, and localizes change (a token or primitive change touches one layer). Keeping
presentational components pure is what makes them reusable and testable and keeps features decoupled from
the design system (§4.3–§4.5). Wrapping primitives protects the product from primitive/stack churn and
concentrates accessibility/token binding in one place.

## Alternatives Considered

- **Using shadcn primitives directly in features/screens** — rejected: scatters token/a11y binding,
  couples every screen to the primitive library, makes a swap a rewrite (contra §4.14, frozen handoff).
- **Inheritance-based component hierarchy** — rejected: rigid, opaque, hard to test (contra §4.4).
- **No presentational/feature separation** — rejected: features would bloat with logic and lose reuse; the
  design system would leak feature concerns (contra §4.3).

## Trade-offs

- **Wrapping overhead vs. insulation:** wrappers add a thin layer over primitives, but buy token/a11y
  consistency and swap-ability. Accepted.
- **Purity vs. convenience:** keeping presentational components logic-free sometimes means more wiring in
  feature components; justified by reuse and testability.

## Risks

- **Layer violations** (a lower component importing a higher one, or a screen importing a primitive).
  *Mitigation:* dependency rules + enforcement ([02.7](02.7_Module_Dependency_Rules.md)).
- **Prop-interface drift** from the frozen design (variants/states not in the spec). *Mitigation:* 1:1 with
  Component Mapping; Design QA.
- **Premature promotion** bloating the shared layer. *Mitigation:* proven-need + governance gate (AD-6).

## Future Extension Points

- New design-system components (via design CR) enter at their correct layer with a full spec.
- New feature components compose the existing layers — additive, no core change (§4.14).
- A primitive/library change is absorbed at the wrapper layer only (§4.12, §4.14).
