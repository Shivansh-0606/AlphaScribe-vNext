## Purpose

Define the **architectural philosophy** governing synchronization between the frontend and the backend:
who is authoritative, how the client and server reconcile, how reconnection and retries behave, how stale
data and conflicts are treated, and how unsaved work is preserved and resumed. This document exists to make
synchronization behavior **predictable and principled** so no engineer must invent it. It is philosophy
only — it defines **principles, not mechanisms**.

## Scope

**In scope:** synchronization ownership and authority (client vs. server), reconnect philosophy, retry
philosophy, stale-data philosophy, synchronization boundaries, conflict detection and resolution
philosophy, unsaved-draft preservation, resume-after-reconnect, and the interaction with **Never Lose
Work**.

**Out of scope (explicitly, per the milestone constraints):** APIs, React, Zustand, TanStack Query
internals, algorithms, protocols, and any implementation. This document names *principles*; the
technologies that realize them are governed elsewhere and unchanged.

## Architectural Principles

1. **The server is the single source of truth; the client holds a reconcilable working copy.** Consistent
   with [03 AD-1](03_Data_and_State_Architecture.md)/[03.2 AD-1](03.2_Server_State_Strategy.md),
   synchronization moves the client *toward* server truth — it is **reconciliation, not a merge of equals**.
2. **Never Lose Work is the overriding constraint.** No synchronization decision — reconnect, retry,
   conflict resolution, or cache expiry — may discard the user's completed or in-progress research (Law 6).
   Where authority and preservation appear to conflict, work is **preserved and surfaced**, never silently
   destroyed.
3. **Honesty about synchronization state.** The interface never presents **unsynced work as synced** or
   **stale data as live** (§4.13, trust-first). Synchronization status is legible; ambiguity is resolved in
   favor of caution and transparency.
4. **Graceful degradation.** Loss of connectivity degrades the experience to a bounded, honest **Offline**
   state (frozen States), not a failure; capability returns automatically or on user action when
   connectivity is restored.
5. **Reconciliation is explicit and predictable.** What synchronizes, when, and in which direction is
   defined by boundaries (below), never by hidden or emergent behavior (§4.10).

## Architectural Decisions

### AD-1 — Synchronization ownership
Reconciliation is owned at the **integration/application boundary** ([02 layers](02_Application_Architecture.md)):
the integration boundary is where client working-state is reconciled against server truth, and the
application layer is where **pending user intent** (unsaved/in-flight work) is tracked until it is
committed. Presentational components never synchronize; they render synchronized state.

### AD-2 — Client authority vs. server authority
- **Server-authoritative:** all **committed, persisted truth** (research sessions, reports, saved data,
  identity/session). The client never overrides it.
- **Client-authoritative (transiently):** **unsaved local intent** — in-progress drafts, ephemeral UI
  state, not-yet-committed edits — is owned by the client **until it is committed**, at which point the
  server becomes authoritative for it.
The boundary is: *the client owns what the user has not yet committed; the server owns everything
committed.*

### AD-3 — Reconnect philosophy
On restored connectivity, the client **reconciles rather than assumes**: it revalidates server truth for
what it is showing, resumes or re-presents pending intent that was awaiting the network, and surfaces
anything that needs the user's attention. Reconnection restores the user to a **consistent, current** state
without losing their place or their unsaved work (Resume Session, J-06).

### AD-4 — Retry philosophy
Retries are **bounded, safe, and non-duplicating**: a retry must never cause a committed effect to happen
twice (safety over eagerness). Operations that are safe to repeat may be retried automatically within
bounds; operations that are not are not blindly retried — they are surfaced for user decision. On retry
exhaustion, the failure becomes a **recoverable Error/Timeout state** ([03.11](03.11_Error_Boundary_and_Recovery.md)),
never a silent drop.

### AD-5 — Stale-data philosophy
Stale data may be shown **only when bounded and clearly framed** (the Offline state; already-fetched
research remains readable during disconnection — [03.5 AD-4](03.5_Caching_Strategy.md)), and **never
presented as live** where currency matters to trust. On reconnect, shown data is revalidated toward server
truth. Freshness is a trust obligation, not merely a performance preference.

### AD-6 — Synchronization boundaries (what syncs, what does not)
- **Synchronizes** (server-owned): research sessions, reports, saved/derived research, identity/session,
  and any persisted user work.
- **Does not synchronize** (client-only, ephemeral): transient UI state, view/interaction state, and other
  data with no server home ([03.1](03.1_State_Management_Strategy.md)).
The synchronization surface is **explicit**; nothing syncs by accident, and ephemeral UI is never pushed to
the server.

### AD-7 — Conflict detection philosophy
A conflict is a **divergence between the client's pending intent and the server's current truth** for the
same committed entity (e.g. the underlying session changed since the client last observed it). Detection is
based on **change markers** the server exposes for its entities (a conceptual "this is the version you
based your change on" signal) — described here as a principle, not a mechanism. The architecture **detects
divergence rather than assuming none**.

### AD-8 — Conflict resolution philosophy
- For **committed truth**, the **server wins** — the client does not overwrite server truth blindly.
- For the user's **unsaved work**, the work is **never silently discarded**: it is **preserved and
  re-surfaced** so the user is never robbed of effort (Law 6), and, where the divergence is meaningful, the
  resolution is **user-mediated** (the user is shown the situation and chooses) rather than resolved by a
  hidden rule. Silent last-write-wins that destroys user work is prohibited.

### AD-9 — Unsaved draft preservation
In-progress, uncommitted work (a draft, an in-flight edit, composer input) is **preserved locally across
disconnection and interruption** and is **not lost** to a network failure, navigation, or timeout — the
direct application of Law 6 at the synchronization layer. Preserved drafts are re-presented or re-submitted
on reconnect (AD-3), subject to the trust and privacy rules ([03.5 AD-5](03.5_Caching_Strategy.md): no
sensitive material persisted beyond the session).

### AD-10 — Resume after reconnect
Reconnection **resumes context, not restarts it**: the user returns to their research subject, session, and
pending work intact (Resume Session, J-06; Context Restored facet). Resumption reconciles to current server
truth while preserving the user's unsaved intent.

### AD-11 — Interaction with Never Lose Work
Never Lose Work (Law 6) is the **dominant principle** across all of the above: reconnect, retry, stale-data,
and conflict decisions are all evaluated first against "does this preserve the user's work?" — and if a
choice would lose work, it is not taken. Synchronization serves preservation; it never overrides it.

## Responsibilities

| Concern | Responsible layer/party |
|---------|-------------------------|
| Authority over committed truth; change markers for conflict detection | **Backend** (§6.2) |
| Reconciliation against server truth; revalidation on reconnect | **Integration boundary** |
| Tracking pending intent; preserving unsaved drafts; retry orchestration (bounded, safe) | **Application layer** |
| Honest presentation of sync/offline/stale state; user-mediated conflict prompts | **UI layer** |
| The Never-Lose-Work guarantee | **All layers** (dominant constraint) |

## Trade-offs

- **Server-authoritative reconciliation vs. offline-write freedom:** treating the server as authority
  simplifies correctness and trust but limits fully offline editing; the measured position preserves and
  reconciles unsaved work rather than pretending an offline write committed. Accepted (trust-first).
- **User-mediated conflict resolution vs. automatic merge:** asking the user on meaningful conflicts adds a
  step but prevents silent work loss; automatic merges are avoided where they could destroy intent.
- **Preservation vs. privacy:** preserving drafts must respect the no-sensitive-persistence rule; drafts are
  preserved within the session boundary, not indefinitely.

## Risks

- **Silent overwrite of user work** (last-write-wins destroying intent). *Mitigation:* AD-8 preserve-and-
  surface + user-mediated resolution; Law 6 dominance (AD-11).
- **Stale-as-live** after reconnect. *Mitigation:* revalidation (AD-3/AD-5); honesty principle.
- **Duplicated effects from retries.** *Mitigation:* bounded, non-duplicating retry (AD-4).
- **Unbounded local persistence of sensitive drafts.** *Mitigation:* session-scoped, non-sensitive
  preservation (AD-9; [03.5 AD-5](03.5_Caching_Strategy.md)).

## Future Extension Points

- **Full offline-first editing** (queued offline writes reconciled on reconnect) is a natural future
  extension of AD-2/AD-4/AD-9; the philosophy here already governs it, so adopting it is additive and does
  not change these principles (§4.14).
- **Richer conflict UX** (structured diff/merge assistance) can extend AD-8 without altering the server-
  authoritative rule.
- **Real-time synchronization** (live server push) extends AD-3/AD-5 while keeping server authority.
