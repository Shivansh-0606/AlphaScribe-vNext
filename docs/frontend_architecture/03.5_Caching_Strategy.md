## Purpose

Define the **caching philosophy** for server state: what the cache is (and is not), how freshness and
invalidation work, when caching may be offline-friendly, and how caching upholds trust (never stale-as-
fresh) and never-lose-work — without becoming a second source of truth.

## Scope

**In scope:** cache role, freshness/invalidation, mutation-driven updates, offline-friendly caching,
privacy/session boundaries of the cache. **Out of scope:** client/UI state ([03.1](03.1_State_Management_Strategy.md)),
fetching ([03.4](03.4_Data_Fetching_Strategy.md)), implementation.

## Architectural Decisions

### AD-1 — The cache is a working copy of server truth, never a second authority
The TanStack Query cache holds server state client-side for performance and continuity, but the **server
remains the single source of truth** ([03.2 AD-1](03.2_Server_State_Strategy.md)). The cache accelerates and
bridges; it never *overrides* server truth or becomes an independent store of record (§4.10).

### AD-2 — Freshness by data volatility (no stale-as-fresh)
Cache freshness is set by how volatile the data is ([03.2 AD-3](03.2_Server_State_Strategy.md)):
slow-changing data (filed statements, historical filings) is cached longer and background-revalidated;
session/report data is kept consistent with saved work; live/AI output is not cached as reusable truth. The
governing trust rule: **the UI never presents stale data as current where currency matters** — where it
does, revalidation or an explicit freshness cue applies (§4.13, trust-first).

### AD-3 — Invalidation is targeted and mutation-driven
Mutations ([03.2 AD-4](03.2_Server_State_Strategy.md)) **invalidate or update** the specific server-state
entries they affect, using the semantic query-key hierarchy so related views refresh together and unrelated
data is untouched. Invalidation is explicit and predictable (§4.10), not broad cache-clearing.

### AD-4 — Offline-friendly caching where appropriate (continuity, within trust limits)
To support resilience and **never-lose-work** (Law 6) on imperfect networks:
- **Already-fetched research remains readable** from cache during transient connectivity loss, presented as
  the frozen **Offline** state (limited, honest about connectivity), so the user keeps their place and
  in-progress context rather than losing it.
- **Optional cache persistence** (surviving reload within a session) may be applied to **non-sensitive,
  slow-changing** server state to speed re-entry and Resume Session.
- **Trust guardrail:** offline/persisted data is clearly bounded and never shown as *live*; write/mutation
  actions that need the server degrade gracefully (queued/blocked with a clear message), never silently
  "succeeding" offline.

### AD-5 — Cache respects session and privacy boundaries
Cached server state — which includes sensitive research content — is **scoped to the authenticated
session** and **cleared on logout/session end** ([03.6](03.6_Authentication_Architecture.md)). Sensitive
data is not persisted beyond the session boundary, and never to insecure or shared storage (privacy/security
rules). Persistence, where used, follows an explicit allow-list of non-sensitive data.

## Design Rationale

Treating the cache strictly as a working copy of server truth avoids the classic bug where a client cache
silently diverges into a false authority. Volatility-based freshness balances performance against the
product's non-negotiable trust requirement (no stale financial/AI data shown as current). Bounded offline-
friendliness serves never-lose-work and resilience on imperfect networks without compromising trust or
privacy. Targeted, mutation-driven invalidation keeps the cache correct and predictable at scale.

## Alternatives Considered

- **Aggressive long caching everywhere** — rejected: risks stale-as-fresh on data where currency matters to
  trust (contra trust-first, §4.13).
- **No caching / always-refetch** — rejected: poor performance on imperfect networks, breaks continuity
  (contra §4.7, Law 6).
- **Full offline-first persistence of all data** — rejected for the MVP: privacy/trust complexity outweighs
  benefit; bounded offline read of already-fetched, non-sensitive data is the measured choice (future
  extension available).

## Trade-offs

- **Performance (longer cache) vs. freshness (trust):** tuned per data type; trust wins where currency
  matters. Accepted.
- **Offline continuity vs. complexity/privacy:** bounded offline read adds complexity and requires careful
  session-scoping, but serves never-lose-work; scoped deliberately.

## Risks

- **Stale-as-fresh** on trust-critical data. *Mitigation:* volatility freshness + revalidation + honest
  Offline/partial cues (AD-2/AD-4).
- **Sensitive data lingering in cache/storage.** *Mitigation:* session-scoped cache, clear-on-logout,
  non-sensitive persistence allow-list (AD-5).
- **Invalidation gaps** (stale views after a mutation). *Mitigation:* key-driven targeted invalidation
  (AD-3) + review.

## Future Extension Points

- Full offline-first research (persisted, encrypted, session-bounded) can extend AD-4 via a governed change
  (§4.14) if the roadmap prioritizes it.
- Cross-session, server-owned preferences move volatile UI prefs to server state (out of the client cache).
- Smarter revalidation (e.g. on window focus / reconnect) tunes freshness without changing ownership.
