## Purpose

Define the **validation architecture** — how **Zod** provides one validation vocabulary across the frontend,
where validation happens (the trust boundaries), how schemas double as the source of truth for data shapes,
and how validation enforces Fail Fast and accessible error reporting.

## Scope

**In scope:** validation ownership, validation boundaries (forms, API responses, route params), schemas as
typed contracts, client-vs-server validation roles, error reporting. **Out of scope:** form lifecycle
([03.8](03.8_Form_Architecture.md)); API-client structure ([03.3](03.3_API_Layer_Architecture.md));
implementation.

## Dependencies

[Constitution](01_Frontend_Architecture_Constitution.md) §4.9 (Type Safety), §4.10, §4.13 (Fail Fast), §6;
[03 Data & State](03_Data_and_State_Architecture.md), [03.3 API Layer](03.3_API_Layer_Architecture.md),

## Architectural Decisions

### AD-1 — Zod is the single validation vocabulary
All runtime validation uses **Zod**, giving one consistent way to declare, compose, and enforce data shape
and constraints across the frontend (§4.9). One vocabulary means validation is learnable, reviewable, and
uniform — no ad-hoc hand-rolled checks scattered through the code.

### AD-2 — Validate at every trust boundary
Validation is applied wherever data **crosses a trust boundary** (§4.9, §4.13):
- **Inbound API responses** — validated at the **integration layer** before becoming trusted server state
  ([03.3 AD-4](03.3_API_Layer_Architecture.md)): external/best-effort data is **untrusted until validated**.
- **Form input** — validated before it becomes a submission payload ([03.8](03.8_Form_Architecture.md)).
- **Route/URL params** — validated where they drive data or behavior (predictable, safe routing —
  [02.3](02.3_Routing_Architecture.md)).
Data that is internal and already-trusted is not re-validated needlessly (§4.11); validation guards
**ingress and egress**, not every function call.

### AD-3 — Schemas are the single source of truth for data shape
A Zod schema and its inferred type are **one artifact**: the schema validates at runtime and the derived
type describes the shape at compile time. This prevents drift between "what we validate" and "what we type"
(§4.9, §4.10). Shared schemas (for cross-feature entities like company, source reference, session) live as
**stable contracts** in shared modules ([02.2](02.2_Feature_Organization.md)) — the single definition both
sides depend on.

### AD-4 — Client validation is UX; the backend remains the authority
Client-side validation exists for **fast, accessible feedback and payload integrity** — it is **not** the
security or business-rule authority. The **backend independently validates and enforces** all rules (§6.2,
§4.13). The frontend never assumes its own validation is sufficient for security; it validates defensively
and defers authority to the server.

### AD-5 — Invalid data fails fast, visibly, and accessibly
Per §4.13: invalid data is **rejected at the boundary** with a clear diagnostic — never silently coerced or
passed through. For user input, errors are surfaced **inline, specific, non-blaming, text-based, and
`aria`-associated**, with focus moved to the first error (frozen [Accessibility](../design/12_Accessibility.md);
[03.8 AD-4](03.8_Form_Architecture.md)). For API responses, a validation failure normalizes to the frozen
**Error/Partial Failure** State ([03.3](03.3_API_Layer_Architecture.md)), protecting trust-critical financial/
AI data from silent corruption.

### AD-6 — Financial and AI data integrity
Given the trust-first product, schemas for financial figures and AI/grounding payloads are treated with
particular rigor: shape, presence of required source/citation references, and type of numeric fields are
validated so the UI never renders malformed or unsourced trust-critical data as valid (upholds the frozen
traceability guarantee at the data boundary).

## Design Rationale

A single validation vocabulary applied at trust boundaries, with schemas doubling as the type source of
truth, is the most reliable way to keep runtime and compile-time views of data in sync and to stop bad data
at the door (§4.9, §4.13). Making client validation explicitly UX-only — with the backend authoritative —
keeps the security model honest. Rigorous validation of financial/AI payloads operationalizes trust-first
at the exact point malformed data could otherwise slip into the interface.

## Alternatives Considered

- **Separate type declarations and runtime checks** — rejected: they drift; the schema-as-source-of-truth
  approach keeps them unified (§4.9).
- **Validating only on the client (trusting it)** — rejected: the client is never the authority (§4.13, §6).
- **Validating everything everywhere (including internal trusted data)** — rejected: needless overhead and
  noise; validation guards boundaries, not every call (§4.11).

## Trade-offs

- **Boundary validation overhead vs. integrity:** validating every response/input costs a little runtime
  and ceremony, but is the price of trust-boundary integrity. Accepted (trust-first).
- **Shared schemas vs. feature autonomy:** shared entity schemas are a shared dependency; justified because
  they are stable contracts and prevent divergent shapes (§4.12).

## Risks

- **Unvalidated path** (a boundary missed). *Mitigation:* boundary validation as an architectural rule +
  review; integration layer as the single inbound gate ([03.3](03.3_API_Layer_Architecture.md)).
- **Schema/backend drift.** *Mitigation:* validation catches mismatches fast (§4.13); shared contract
  governance (§6.3).
- **Over-validation noise.** *Mitigation:* validate ingress/egress only (AD-2, §4.11).

## Future Extension Points

- New entities add schemas (validation + type) behind the same vocabulary (§4.14).
- Shared schema packages can be split out (monorepo) as stable contracts if the team scales.
- Contract-generation from the backend (if adopted) would feed these schemas without changing the strategy.
