## Purpose

Define the **form architecture** — how forms own their state (via **React Hook Form**), their lifecycle
from initialization to submission, how they integrate with validation and mutations, and the accessibility
and security obligations of form handling — without duplicating form state into client or server state.

## Scope

**In scope:** form-state ownership, form lifecycle, submission/mutation integration, controlled-input
philosophy, accessibility and sensitive-field handling. **Out of scope:** validation schema detail
([03.9](03.9_Validation_Strategy.md)); server mutations detail ([03.2](03.2_Server_State_Strategy.md));
implementation; designing the forms (frozen UX).

## Architectural Decisions

### AD-1 — Form state is owned by React Hook Form, isolated from client/server state
In-progress form input is its **own state category**, owned by **React Hook Form** ([03 AD-1](03_Data_and_State_Architecture.md)),
**not** duplicated into Zustand or the Query cache. This isolation prevents cross-contamination and keeps
each state category single-owned. Initial values may be **seeded** from server state (e.g. current
settings), but the working copy lives in the form until submission.

### AD-2 — Form lifecycle
```
Initialize (default/seeded values, schema attached) → Edit (validate on the frozen cadence) →
Submit (validated payload → Application-layer use-case → mutation → backend) →
Success (confirm; server state updated/invalidated) │ Error (surface, PRESERVE input, focus first error)
```
- **Initialization:** default or server-seeded values; the validation schema ([03.9](03.9_Validation_Strategy.md))
  is bound to the form.
- **Editing/validation:** validation follows the frozen [Forms interaction pattern](../design/10_Interaction_Patterns.md)
  (inline, specific); errors are accessible and associated with their field.
- **Submission:** produces a **validated, typed payload** submitted via a mutation ([03.2 AD-4](03.2_Server_State_Strategy.md));
  the form does not call the network directly ([02.7](02.7_Module_Dependency_Rules.md)).
- **Outcome:** success confirms and lets the user continue (frozen Success State); error **preserves the
  user's input** and moves focus to the first error (never clears the form — Law 6, §4.13; frozen a11y).

### AD-3 — Controlled/uncontrolled and performance
Forms follow RHF's efficient model (minimize re-renders); the choice of controlled vs. uncontrolled per
field is an implementation detail bounded here only by the requirement that it not compromise accessibility
or validation timing. Field components are the frozen design-system inputs ([02.5](02.5_Component_Architecture.md)),
wired to the form — presentational inputs never own submission logic.

### AD-4 — Accessibility is structural to forms
Per frozen [Accessibility](../design/12_Accessibility.md): every field has a visible programmatic label;
errors are text, specific, and `aria`-associated; **focus moves to the first invalid field** on failed
submit; required/invalid states are exposed (`aria-required`/`aria-invalid`), never color-only. These are
non-negotiable form obligations (§4.6).

### AD-5 — Sensitive fields: strict handling (security/privacy)
Password and API-key fields (Auth, AI Setup / `AIAccessSelector`) are handled under strict rules: **masked
values are never announced back** (frozen a11y), **never logged, never persisted client-side, never placed
in URLs**, and are transmitted only through the integration layer to the backend
([03.6](03.6_Authentication_Architecture.md)/[03.3](03.3_API_Layer_Architecture.md)). The frontend holds
such material only transiently, in the form, until submission.

### AD-6 — Forms surface all relevant frozen States
A form renders the applicable frozen [States](../design/13_States.md): submitting (Loading), Success, Error,
and — for AI-access validation — Validating/Valid/Invalid/Permission Denied. No form dead-ends; every error
offers a recovery.

## Design Rationale

Isolating form state in RHF keeps the data taxonomy clean (no duplication) and gives efficient, accessible
form handling with minimal re-renders. Routing submission through a mutation (not a direct fetch) preserves
the layered architecture and single trust boundary. Preserving input on error and moving focus to the first
error operationalize never-lose-work and the frozen accessibility contract at exactly the point users are
most likely to make mistakes. Strict sensitive-field handling protects the product's security/privacy posture.

## Alternatives Considered

- **Form values in a global store (Zustand)** — rejected: duplicates state, couples forms to global state,
  re-render cost (contra §4.3, "prevent duplicated state").
- **Uncontrolled DOM-only forms without a form library** — rejected: harder to enforce validation timing,
  accessibility, and typed payloads consistently (contra §4.9, §4.6).
- **Clearing the form on submission error** — rejected: destroys user work (contra Law 6).

## Trade-offs

- **Form library vs. raw inputs:** RHF adds a dependency but standardizes validation, performance, and a11y
  wiring; justified and stack-approved (§5.4).
- **Seeding from server state vs. always-blank:** seeding improves UX (edit-in-place) but requires care that
  the form copy, not the cache, is edited; handled by the ownership rule (AD-1).

## Risks

- **Form state leaking into client/server state.** *Mitigation:* AD-1 isolation + review.
- **Lost input on error.** *Mitigation:* preserve-and-focus rule (AD-2/AD-4).
- **Sensitive field mishandling.** *Mitigation:* AD-5 strict rules; never log/persist/announce/URL.

## Future Extension Points

- New forms (future features) adopt the same lifecycle + schema-bound validation (§4.14).
- Multi-step/wizard flows (should any arise) extend the lifecycle while keeping per-step state in the form
  and only committing on final submit.
- Autosave of non-sensitive drafts (if ever wanted) would move drafts to server state via a governed change,
  not into a client store.
