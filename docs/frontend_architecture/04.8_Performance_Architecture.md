## Purpose

Define the **performance architecture** that makes AlphaScribe fast and responsive on imperfect networks —
the performance-oriented rendering practices, budgets, and perceived-performance approach — as **Performance
by Design** (Constitution §4.7), not a later optimization pass. It delivers the frozen performance-aware
design principles (§21) and the M2/M3 rendering and data strategies; it defines no new UX.

## Scope

**In scope:** performance-oriented rendering practices (server/client split, hydration, code-splitting,
streaming), performance budgets, perceived performance, asset performance, and performance observability.
**Out of scope:** micro-optimization tactics/implementation, backend performance (§6.2), and redesigning UX.

## Architectural Decisions

### AD-1 — Performance is designed in, measured against budgets
Performance is a **first-class architectural property** (§4.7), governed by **performance budgets** (e.g.
payload/JS size per route, interaction latency, Core-Web-Vitals-oriented targets). Budgets constrain growth:
a change that regresses a budget is a reviewable regression, not an afterthought. (Specific budget numbers
are set with Engineering; the architecture fixes that budgets govern.)

### AD-2 — Server-first rendering minimizes client cost
Per Constitution §7 and [02.6](02.6_UI_Layer_Architecture.md): **server rendering is the default** for
content-led, read-heavy surfaces (statements, filings, reports), minimizing shipped JavaScript and improving
first paint on imperfect networks; **client rendering is reserved** for genuine interactivity/live experience
(AI companion, streaming, forms). This split is the primary performance lever.

### AD-3 — Hydration is minimized via scoped client islands
Interactivity is confined to **tightly scoped client islands** ([02.6 AD-2](02.6_UI_Layer_Architecture.md)),
so hydration cost is bounded to where interaction is real — the rest stays server-rendered and cheap. Islands
are as small as the interaction requires (§4.7).

### AD-4 — Code-splitting by route and feature
Code is **split along route and feature boundaries** ([02.2](02.2_Feature_Organization.md), [02.3](02.3_Routing_Architecture.md)):
a surface loads what it needs, deferring the rest. This aligns performance boundaries with the architecture's
module boundaries — feature isolation doubles as a performance boundary (§4.5, §4.7).

### AD-5 — Perceived performance leads (progressive, streamed, skeletoned)
Delivering §21 and [04.7](04.7_Loading_Empty_and_Error_Experience.md): **immediate acknowledgment**,
**skeletons that preserve layout**, **progressive reveal** (summary before detail per the frozen IA), and
**streaming** (AI + progressive content) — favoring *perceived* speed and visible progress over waiting for
completeness. Data fetching is parallelized and summary-first ([03.4](03.4_Data_Fetching_Strategy.md)); caching
serves continuity ([03.5](03.5_Caching_Strategy.md)).

### AD-6 — Asset and rendering efficiency
Assets follow the frozen [Asset Export Standards](../experience_design/engineering_handoff/08_Asset_Export_Standards.md)
(SVG-first, optimized, appropriately sized raster); fonts (IBM Plex) are loaded to avoid layout shift;
animation is compositor-friendly and non-blocking ([04.6 AD-5](04.6_Motion_Architecture.md)); images/media are
sized and lazy-loaded where appropriate. Fewer, purposeful elements render faster and read clearer (§21).

### AD-7 — Performance is observable
Performance is **measured, not assumed** (§4.15): the architecture provides for capturing performance and
Core-Web-Vitals-style signals and user-perceived timings (privacy-safe), so regressions are visible in
production and budgets are enforceable. (Tooling deferred to the observability milestone; the *intent* to be
measurable is fixed here.)

## Design Rationale

The frozen product must feel fast for research on imperfect networks; that is only achievable if performance
is architectural — a server-first rendering strategy, bounded hydration, feature/route code-splitting, and a
perceived-performance-first approach — governed by budgets and made observable. Aligning performance
boundaries with the module architecture means the same structure that gives maintainability also gives
performance. This delivers §21 and §4.7 faithfully without changing any UX.

## Alternatives Considered

- **Client-rendered SPA** — rejected: larger payloads, worse first paint/SEO, more hydration (contra §7, §4.7).
- **Optimize-later** — rejected: performance retrofits are expensive and partial; it is designed in (§4.7).
- **Waiting for completeness before render** — rejected: violates perceived-performance and summary-before-
  detail (§21); progressive/streamed rendering is used.

## Trade-offs

- **Server-first vs. interaction latency:** some interactions incur a round-trip; mitigated by islands +
  prefetch/streaming (§7). Accepted for payload/first-paint/SEO gains.
- **Budgets vs. feature freedom:** budgets constrain what a surface can ship, but that constraint keeps the
  product fast as it grows. Accepted.
- **Perceived-performance complexity vs. simplicity:** progressive/skeleton/stream is more complex than
  fetch-all-then-render, but it is the frozen requirement; complexity is contained in the data/state layers.

## Risks

- **Bundle/hydration bloat** over time. *Mitigation:* budgets (AD-1) + code-splitting (AD-4) + observability
  (AD-7).
- **Over-client rendering** harming performance. *Mitigation:* server-first default + scoped islands (AD-2/3).
- **Slow best-effort sources stalling a surface.** *Mitigation:* parallel/partial/progressive fetching
  ([03.4](03.4_Data_Fetching_Strategy.md)) + Partial Failure/Timeout ([04.7](04.7_Loading_Empty_and_Error_Experience.md)).

## Future Extension Points

- Concrete budgets and Core-Web-Vitals targets are set with Engineering and tracked in CI.
- Prefetch heuristics (anticipating the next research step) can enhance perceived performance behind the same
  data layer.
- Edge rendering/caching (if adopted) extends the server-first strategy without changing the model.
- Performance observability tooling attaches at AD-7's seam in the observability milestone (§4.15).
