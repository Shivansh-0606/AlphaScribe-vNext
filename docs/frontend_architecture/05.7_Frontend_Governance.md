## Purpose

Define the **governance model** that keeps the Frontend Architecture coherent and authoritative over time —
ownership, the Change Request process, review gates, approval, versioning, and how the architecture is
maintained after freeze. It **consolidates and operationalizes** Constitution §12; it changes no principle.

## Scope

**In scope:** ownership model, CR process, review workflow and gates, approval, versioning, and maintenance/
deprecation governance for the Frontend Architecture. **Out of scope:** product/design governance (owned
elsewhere, referenced), and implementation.

## Architectural Decisions

### AD-1 — Ownership model
| Layer | Owner | Authority |
|-------|-------|-----------|
| Product scope, IA, navigation, features | **Product** (frozen) | change via CR + CTO |
| Design Constitution & visual/experience system, tokens | **Design / Experience Design** (frozen) | change via CR |
| Frontend architecture (M1–M5) | **Frontend Architecture** | change via CR |
| Component/state/data/config implementation | **Frontend Engineering** | within the architecture contract |
| The architecture as a shared asset | **Architecture stewards** (a named Architecture+Eng pair) | triage CRs/ADRs, maintain the package |
| Final adjudication / freeze | **CTO** | approves/rejects CRs & ADRs |

The bright line (§6.5, [M2 §6](02_Application_Architecture.md)): **Architecture decides structure and
rationale; Engineering decides how to build within it.** Ambiguity → CR/ADR.

### AD-2 — The Change Request (CR) process governs all changes to frozen artifacts
Any change to **frozen upstream** (Product/Design/Experience) or the **frozen architecture (M1–M5)** or the
**approved stack** is made only through a CR (§12): problem → traceability → impact/risk → recommendation →
**CTO decision** (Approve/Reject/Defer) → update artifact(s) + dependents together → version bump →
communicate. Frozen documents are **never edited directly**. This uses the existing [Documentation
Governance](../governance/Documentation_Governance.md) and [CR Register](../governance/change_requests/00_Change_Request_Register.md).

### AD-3 — Review workflow and gates
A change merges only through the gates: **architecture review** (consistency with frozen upstream, principle
compliance, accessibility, dependency rules), **engineering review** (correctness/types/perf), **the
[Architecture Review Checklist](05.9_Architecture_Review_Checklist.md)**, **Design QA** (for experience-
affecting work — Experience handoff), and — for frozen-scope changes — **CTO approval**. Significant decisions
are captured as **ADRs** ([05.6](05.6_Architecture_Decision_Record_Index.md)). Sign-offs are recorded.

### AD-4 — Approval and freeze
A document/decision is eligible for approval only when it meets the **Definition of Done** (§13) and passes
review; **CTO approval freezes** it, after which it changes only via CR. Architecture that violates a
constraint (§5) or an Immutable Law of the Design Constitution cannot be approved.

### AD-5 — Versioning
The architecture package uses **semantic versioning** ([05.2](05.2_Documentation_Standards.md)): major =
substantive/breaking (re-review), minor = additive, patch = fixes. Related artifacts (docs, ADRs) are
versioned consistently; superseded content is retained in history.

### AD-6 — Maintenance and deprecation
Documentation is maintained with the change (never drift); **code that diverges from the frozen architecture
is a defect** ([05.2 AD-5](05.2_Documentation_Standards.md)). Deprecation (of a pattern, dependency, or
decision) follows **mark → migrate → confirm no references → remove/supersede**, communicated with a
migration path ([05.5](05.5_Dependency_Guidelines.md), [05.6](05.6_Architecture_Decision_Record_Index.md)).

## Design Rationale

Explicit governance is the difference between an architecture that compounds in value and one that forks and
rots under many hands. CR-gating changes to frozen scope protects the product's core promises from erosion
"one small decision at a time" (Constitution §Purpose); named stewards give CRs/ADRs an owner so triage does
not stall; and consistent versioning + maintenance discipline keep the package trustworthy. This
consolidates the Constitution's governance into an executable model.

## Alternatives Considered

- **Informal governance** — rejected: erodes under pressure; §12 requires enforceable gates.
- **Editing frozen docs directly** — rejected: inverts authority; changes go through CR.
- **No named stewards** — rejected: CRs/ADRs stall without owners.

## Trade-offs

- **Governance overhead vs. coherence:** gates and CRs add process, but the cost is far below the cost of
  drift/forks. Accepted.
- **CR-gating vs. speed:** changing frozen scope is deliberately slower, protecting the product's guarantees.
  Accepted.

## Risks

- **Governance bypassed under pressure.** *Mitigation:* review gates as merge requirements (AD-3) + stewards.
- **Drift between code and architecture.** *Mitigation:* AD-6 (code drift is a defect).
- **Stalled CRs/ADRs.** *Mitigation:* named stewards (AD-1) + CTO adjudication.

## Future Extension Points

- Additional stewards/roles as the team scales; automated gate checks (link/structure/boundary linting).
- Governance extends to future architecture milestones and any sub-departments.
