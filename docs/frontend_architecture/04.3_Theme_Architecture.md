## Purpose

Define the **theme architecture**: how the application delivers the **single, frozen light theme**, and how
theming is *structured* so a future theme could be introduced without re-work — **without adding a theme,
a toggle, or a dark mode** (all frozen out for the MVP). This document honors, and does not alter, the
frozen single-theme decision.

## Scope

**In scope:** the single-theme delivery structure, the theming model (semantic roles → one token set), and
the future-themability extension point. **Out of scope:** introducing a second theme or a theme toggle
(frozen; CR-only), modifying tokens ([04.2](04.2_Design_Token_Consumption_Strategy.md); §5.3), and
implementation.

## Architectural Decisions

### AD-1 — One theme, one token set, no toggle (frozen)
AlphaScribe ships a **single warm-light theme** expressed as **one semantic token set** ([04.2](04.2_Design_Token_Consumption_Strategy.md));
there is **no theme toggle and no second (dark) token set** (frozen Design System, Visual Language, Design
Tokens). The theme architecture delivers exactly this and introduces no alternative.

### AD-2 — Theming via semantic CSS variables (a role indirection)
The theme is delivered as the **semantic CSS-variable layer** ([04.2 AD-2](04.2_Design_Token_Consumption_Strategy.md)):
components consume **roles** (`--background`, `--foreground`, `--brand-from`, …), and the role → value
mapping lives in one place. This **role indirection is the theming seam** (§4.12): today it resolves to the
one frozen light theme; it is the single point at which any future theme would attach.

### AD-3 — Minimal theme provision
Because there is exactly one theme, theme "provision" is **minimal**: the app applies the single token set
at the root (via the token layer, [04.2](04.2_Design_Token_Consumption_Strategy.md)); there is **no runtime
theme-switching machinery, no persisted theme preference, and no per-user theme state** ([03.14](03.14_Data_Ownership_Matrix.md)
records "theme is fixed — no toggle"). This keeps the infrastructure simple (§4.11) and faithful to the
frozen decision.

### AD-4 — Themability is preserved structurally, not built
The **structure** is future-themable at no present cost: because consumption is role-based (AD-2), a future
theme would be a **second mapping of the same semantic roles** to a second token set — requiring **no change
to component consumption**. This is a *latent* capability of the token architecture, explicitly **not
implemented** for the MVP (consistent with the frozen docs, which already describe a future theme this way).

### AD-5 — A second theme is a governance decision (CR-VIS-04)
Introducing any additional theme (notably dark mode) is a **frozen-scope change** requiring a **Change
Request** (CR-VIS-04) with Design authority (§6.5, §5.3). The theme architecture does not pre-empt that
decision; it only ensures the door is not architecturally bolted shut.

## Design Rationale

Delivering exactly one theme — with theming expressed as a role indirection — gives the simplest possible
theme infrastructure that is still future-proof: the app is faithful to the frozen single-light-theme
identity today, carries no unused theming machinery, and yet could adopt a future theme as a pure token-set
addition. This honors the frozen decision, avoids speculative complexity (§4.11 YAGNI), and keeps the
extension path open per progressive decoupling (§4.14).

## Alternatives Considered

- **Building a theme system / dark mode now** — rejected: the single light theme is frozen (Design System);
  building an unused theme system violates YAGNI (§4.11) and the constraints.
- **Hardcoding the light palette (no role indirection)** — rejected: forfeits the near-free future
  themability and re-couples components to literal values (contra §4.12, [04.2](04.2_Design_Token_Consumption_Strategy.md)).
- **A user theme preference** — rejected: no toggle exists (frozen); no theme state is stored.

## Trade-offs

- **Role indirection vs. directness:** consuming roles is a hair more indirect than literals, but it is the
  same indirection tokens already require, and it keeps future themability free. Accepted.
- **No theming machinery vs. future readiness:** shipping no runtime theme switch is simpler and correct for
  one theme; a future theme would add the (small) switch then, via CR. Accepted.

## Risks

- **Accidental introduction of a second theme / toggle.** *Mitigation:* AD-1/AD-5 — any theme change is a CR;
  Design QA guards against unsanctioned palettes.
- **Hardcoded colors bypassing the role layer.** *Mitigation:* token-consumption enforcement ([04.2 AD-5](04.2_Design_Token_Consumption_Strategy.md)).

## Future Extension Points

- **A future theme (e.g. dark)** attaches as a second token-set mapping of the same roles via **CR-VIS-04** —
  no component change (§4.14). This is the sole intended extension.
- Per-surface theming (e.g. a print/export theme, already implied by the serif PDF export) would follow the
  same role-mapping approach, scoped and governed.
