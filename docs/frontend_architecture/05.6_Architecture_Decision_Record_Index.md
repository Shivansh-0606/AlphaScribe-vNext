## Purpose

Establish the **Architecture Decision Record (ADR) index and lifecycle** for Frontend Architecture — the
register, template, status lifecycle, approval workflow, and traceability rules from Constitution §11 — and
identify the **candidate ADRs** that formalize decisions already made across M1–M4. It **records** decisions;
it makes none.

## Scope

**In scope:** the ADR register/index, the ADR template and lifecycle, the approval workflow, traceability
rules, and a list of candidate ADRs to formalize. **Out of scope:** making new architectural decisions, and
implementation. Individual ADR files (an `adr/` directory) are created **when the ADRs are authored** under
governance — not in this milestone (which creates only the listed files).

## Architectural Decisions

### AD-1 — The ADR register is the index of significant decisions
ADRs capture **significant architectural decisions** — those costly to reverse, affecting boundaries/public
architecture, introducing/removing a significant dependency, or resolving a non-obvious trade-off (§11). This
document is their **index**; each ADR is a separate record (authored under governance in an `adr/` directory
created at that time).

### AD-2 — ADR template (per §11)
Each ADR contains: **ID & Title · Status · Date & Author · Context · Decision · Rationale · Alternatives
considered · Consequences (trade-offs) · Traceability** (frozen artifacts and related ADRs it serves).

### AD-3 — ADR lifecycle & status values
`Proposed` → `Accepted` → (later) `Deprecated` or `Superseded` (by a named ADR); a proposal may be
`Rejected`. An accepted ADR is **never edited to reverse a decision** — a new ADR supersedes it, preserving
history (§11).

### AD-4 — Approval workflow
An ADR is drafted (`Proposed`), reviewed against the Constitution and frozen upstream, and **`Accepted` on
CTO approval** for significant decisions; it is then binding. Superseding/deprecating follows the same path.
Consequential implementation follows the ADR; a deviation is itself an ADR/CR, never a silent code choice.

### AD-5 — Traceability requirements
Every ADR references the frozen artifact(s) and architectural requirement(s) it serves; architecture
documents cite the ADRs governing their significant decisions; the register links each ADR to its milestone
and status (§11).

## Design Rationale

A register with a fixed template, lifecycle, and traceability makes the *why* behind significant decisions
durable and auditable, and gives future engineers a single place to understand — and safely change — the
architecture's load-bearing choices. Listing candidate ADRs from M1–M4 turns implicit, distributed decisions
into a traceable set without inventing anything, readying the package for a clean decision history.

## Alternatives Considered

- **No ADRs (decisions only in prose)** — rejected: the *why* and alternatives get lost; §11 requires ADRs
  for significant decisions.
- **Authoring all ADR files now** — deferred: ADR files are created under governance when authored; this
  milestone creates only the specified files and establishes the index.
- **Editing accepted ADRs to change decisions** — rejected: supersede-don't-edit preserves history (AD-3).

## Trade-offs

- **ADR overhead vs. durable rationale:** writing ADRs for significant decisions is extra work but preserves
  the reasoning that prevents costly re-litigation. Accepted.
- **Index-now, author-later vs. all-now:** establishing the index and candidates now, authoring under
  governance, respects scope while capturing the decisions. Accepted.

## Risks

- **Significant decisions made without an ADR.** *Mitigation:* review gate ([05.9](05.9_Architecture_Review_Checklist.md))
  + governance ([05.7](05.7_Frontend_Governance.md)).
- **ADRs drifting from reality.** *Mitigation:* supersede-don't-edit + traceability (AD-3/AD-5).

## Future Extension Points

- The `adr/` directory and individual records are created when the candidate ADRs are authored/accepted.
- New significant decisions add ADRs; the register grows as the architecture evolves.
