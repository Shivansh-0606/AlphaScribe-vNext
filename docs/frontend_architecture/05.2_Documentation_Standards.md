## Purpose

Define the **documentation lifecycle and standards** for Frontend Architecture artifacts — the required
structure, metadata, versioning, revision history, review→approval→freeze flow, and maintenance rules — so
the documentation stays a **trustworthy, navigable, and current** reference across the product's life. It
formalizes the conventions already used across M1–M4.

## Scope

**In scope:** the documentation structure/metadata standard, versioning, revision history, the lifecycle
(draft→review→approval→freeze→change), maintenance rules, and onboarding readability. **Out of scope:**
product/design documentation (owned elsewhere), and implementation.

## Architectural Decisions

### AD-1 — Every architecture document follows the required structure
Per Constitution §10, each standard Frontend Architecture document contains, in order: **Purpose · Scope ·
Dependencies · Architectural Decisions · Design Rationale · Alternatives Considered · Trade-offs · Risks ·
Future Extension Points · References**. (The M1 Constitution and M5 governance docs use the section set
appropriate to their type.) This uniform structure is what makes the package predictable and reviewable.

### AD-2 — Standardized metadata on every document
Every document carries a consistent **header** (Document Status, Version, Owner, Approved By, Department /
Milestone, Governed by, Last Updated), a **Revision History** table, and a **footer** version line — the
standard established and normalized across M1–M4. Department naming ("Frontend Architecture") and milestone
naming ("Mn — <Name>") are uniform.

### AD-3 — Semantic versioning of documents
Documents use **semantic versions**: **major** = a substantive change requiring re-review; **minor** =
additive clarification/refinement; **patch** = fixes. A version change is recorded in the Revision History
with author, date, status, and description. Superseded content is retained in history, not erased.

### AD-4 — The documentation lifecycle
```
Draft → Internal review (consistency, principle-compliance, accessibility, feasibility)
      → Cross-document review (coherence across the package) → CTO review → Approved / Frozen
      → Change only via CR (Governance) — never silent edits to a frozen doc
```
This mirrors the Constitution's review/governance flow (§12) and the frozen [Documentation Governance](../governance/Documentation_Governance.md).

### AD-5 — Docs are maintained with the change; code drift is a defect
Documentation is updated **in the same change** that alters what it documents (via CR for frozen docs) —
never after the fact. **Code that drifts from the documented architecture is a defect**, not a reason to edit
the docs to match; the frozen upstream is authoritative ([05.7](05.7_Frontend_Governance.md)). The
source-of-truth hierarchy resolves conflicts (higher wins).

### AD-6 — Documentation serves onboarding and traceability
Documents are written for a future engineer to **understand, navigate, and act** without tribal knowledge:
clear architecture language, cross-references and navigation aids (e.g. the M4 overview/cross-reference
matrix), and **traceability** — every significant decision references the frozen intent it serves and, where
warranted, an ADR ([05.6](05.6_Architecture_Decision_Record_Index.md)).

## Design Rationale

Uniform structure, standardized metadata, semantic versioning, and a disciplined lifecycle are what let a
large documentation set stay coherent and trusted over years and many contributors. Making docs maintained-
with-the-change and treating code drift as a defect prevents the classic rot where documentation silently
becomes fiction. Optimizing for onboarding and traceability is what makes the package usable as the team
grows.

## Alternatives Considered

- **Free-form documents** — rejected: inconsistent, hard to review/navigate; the fixed structure is the
  reviewability mechanism (§10).
- **Docs updated after code (or not at all)** — rejected: guarantees drift; docs are updated with the change
  (AD-5).
- **Editing frozen docs to match drifted code** — rejected: inverts authority; code is the defect, docs
  change via CR.

## Trade-offs

- **Structure/metadata overhead vs. consistency:** the fixed format adds ceremony but is what makes the
  package predictable and maintainable. Accepted.
- **Docs-with-change discipline vs. speed:** updating docs alongside changes slows a change slightly but
  prevents costly drift. Accepted.

## Risks

- **Doc drift** despite the rule. *Mitigation:* AD-5 + review gates ([05.9](05.9_Architecture_Review_Checklist.md)).
- **Inconsistent metadata over time.** *Mitigation:* the standardized header/revision/footer (AD-2) + review.
- **Unnavigable growth.** *Mitigation:* navigation aids (indexes, cross-reference matrices) + the ADR index.

## Future Extension Points

- A documentation linter could enforce the structure/metadata standard automatically.
- Auto-generated indexes/link-checkers extend navigation and traceability.
- The standard extends to future milestones and any new architecture sub-departments.
