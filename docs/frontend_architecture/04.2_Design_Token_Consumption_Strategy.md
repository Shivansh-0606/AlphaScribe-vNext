## Purpose

Define how the **frozen design tokens** are **consumed** by the application — the consumption model, the
delivery mechanism (CSS variables via Tailwind CSS v4), and the enforcement that keeps consumption
disciplined ("tokens or nothing"). This document **consumes and never modifies** the frozen
[Design Tokens](../experience_design/10_Design_Tokens.md) and the frozen
[Token Mapping handoff](../experience_design/engineering_handoff/03_Design_Token_Mapping.md).

## Scope

**In scope:** the token-consumption model, the CSS-variable/Tailwind-v4 delivery layer, semantic consumption
rules, and enforcement of token discipline. **Out of scope:** defining or changing token values (frozen;
§5.3, constraint), theme structure ([04.3](04.3_Theme_Architecture.md)), and implementation.

## Architectural Decisions

### AD-1 — Two-tier consumption: primitive values → semantic tokens → usage
Consumption follows the frozen [Token Mapping](../experience_design/engineering_handoff/03_Design_Token_Mapping.md)
model (restated, not changed):
```
Tier 1  Primitive values      the frozen numbers/hex/HSL in Design Tokens (the ONLY place raw values live)
Tier 2  Semantic CSS variables generated from Tier 1; delivered via Tailwind v4 @theme
Tier 3  Consumption           components use semantic utilities / variables — never raw values
```
The generated Tier-2 layer is **single-sourced from the frozen Design Tokens** and never hand-edited.

### AD-2 — CSS variables (via Tailwind v4 `@theme`) are the single delivery mechanism
Tokens are delivered as **CSS custom properties** consumed through Tailwind v4's `@theme` mapping (the stack
choice, §5.4), matching the frozen model (HSL vars consumed via `hsl(var(--token))`). **shadcn primitives'
theme variables are bound to the same tokens** ([04.1](04.1_Design_System_Integration.md)) — one palette,
no parallel token set.

### AD-3 — Tokens or nothing (the consumption discipline)
Every visual value in a component references a **token** ([04.2 Tier-3]); a raw hex/px/ms/z-index in
component code is a **defect** (§4.10; frozen Token Mapping "tokens or nothing"). A needed value that does
not exist is added as a **token in the owning frozen Experience doc via CR** — never as an inline literal or
a locally-defined value.

### AD-4 — Semantic consumption (roles, not appearances)
Components consume **semantic roles** (`--background`, `--foreground`, `--brand-from`, `--space-4`,
`type.figure`, `--elevation-2`, `--radius-md`, `--focus-ring-*`, `--motion-duration-base`, …), never
appearance literals — so meaning drives usage and the (single) theme is centrally controlled (§4.10; frozen
Color/Token semantics). The signature signal (`--brand-from/--brand-to/--ring`) is consumed only where the
frozen rules permit (primary action, AI/verified/evidence, focus).

### AD-5 — Consumption is enforced
Token discipline is **enforced, not trusted**: a lint rule fails CI on raw values in component styles, and
the Design QA token-compliance pass verifies consumption ([Design QA](../experience_design/engineering_handoff/10_Design_QA_Process.md);
§4.13). This is how token consistency holds across hundreds of screens (quality requirement).

## Design Rationale

A single, generated, semantic token layer consumed via CSS variables is the mechanism that guarantees the
frozen visual identity is applied identically everywhere and can never drift into hardcoded values. Binding
shadcn to the same variables means the design system inherits the palette for free. Enforcing "tokens or
nothing" makes the consistent path the only path — the reliable way to keep a large product on one visual
system. Keeping values frozen and consumed-only preserves design authority (§6.5, §5.3).

## Alternatives Considered

- **Hardcoded values / per-component styles** — rejected: guarantees drift and breaks the single identity
  (contra §4.10, the token-consistency requirement).
- **A parallel token set for shadcn** — rejected: two palettes diverge; shadcn is bound to the frozen tokens.
- **Redefining tokens in the app for convenience** — rejected: tokens are frozen (§5.3); a change is a CR in
  the owning Experience doc.

## Trade-offs

- **Generated layer vs. hand-authored styles:** a generated Tier-2 layer adds a build step but guarantees
  single-sourcing and prevents divergence. Accepted.
- **Strict semantic consumption vs. one-off flexibility:** disallowing literals removes local shortcuts, but
  that is exactly what preserves the system. Accepted.

## Risks

- **Raw values creeping into components.** *Mitigation:* lint gate + Design QA token pass (AD-5).
- **Generated layer drifting from the frozen source.** *Mitigation:* single-source generation; the Tier-2
  layer is never hand-edited; regenerate on token change.
- **Signal overuse** (signature color beyond sanctioned roles). *Mitigation:* semantic consumption rules
  (AD-4) + Design QA.

## Future Extension Points

- A future theme adds a **second Tier-2 mapping** of the same semantic roles ([04.3](04.3_Theme_Architecture.md))
  — zero change to component consumption (§4.14).
- New token families (added by design via CR in the owning Experience doc) flow through the same pipeline.
- A design-tool token export could feed Tier-2 generation, keeping design and code in lockstep.
