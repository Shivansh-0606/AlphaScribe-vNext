## Purpose

Define the **integration (API) layer** — the frontend's single, typed, validated boundary to the backend:
its responsibilities, structure, how remote data becomes trusted frontend models, error normalization, and
the streaming boundary for AI. This is the "trust boundary" of the frontend data architecture.

## Scope

**In scope:** API-layer responsibilities, client structure, request/response contract handling, validation
at the boundary, error normalization, streaming transport, and the frontend/backend split. **Out of scope:**
backend implementation (owned by Backend, §6.2); implementing the client; caching ([03.5](03.5_Caching_Strategy.md)).

## Architectural Decisions

### AD-1 — A single integration layer is the only path to the backend
All backend communication goes through **one integration layer** (the API client + adapters + validation).
**No component, feature UI, or store calls the network directly** ([02.7](02.7_Module_Dependency_Rules.md)
prohibits skipping the application/integration layers). This concentrates the trust boundary, error
handling, and contract knowledge in one place (§4.1, §4.3).

### AD-2 — The API contract is the shared, typed boundary (owned jointly)
The request/response **contract** is the shared boundary between frontend and backend (§6.3): typed on the
frontend, validated at ingress, and changed only by agreement. The frontend **depends on the contract,
never on backend internals** (§4.12); a contract change is a governed event, not an ad-hoc coupling.

### AD-3 — Structure: client · adapters/mappers · validation · error normalization
The integration layer has four internal responsibilities:
- **Client** — issues typed requests (queries/mutations/streams) over the contract; carries session
  context (cookies/opaque token — [03.6](03.6_Authentication_Architecture.md)); applies no business logic.
- **Adapters/mappers** — translate backend response shapes into **frontend domain models** (stable,
  feature-facing shapes), isolating the UI from backend representation drift (§4.1 dependency inversion).
- **Validation** — every response is validated with **Zod at the boundary** before it becomes trusted
  state (§4.9, §4.13; [03.9](03.9_Validation_Strategy.md)): external data is **untrusted until validated**.
- **Error normalization** — transport/protocol/domain failures are normalized into a small, typed error
  vocabulary that maps to frozen [States](../design/13_States.md) (Error, Partial Failure, Timeout,
  Offline, Permission Denied, Auth Required).

### AD-4 — Validation at the boundary enforces Fail Fast
Invalid or unexpected response data **fails fast** (§4.13): it is rejected at the integration boundary with
a clear diagnostic and surfaced as an error State, never silently passed into the cache/UI as if valid. This
protects trust-critical financial/AI data from silent corruption.

### AD-5 — Streaming transport for AI is a first-class integration concern
AI responses are consumed as a **stream** at the integration layer (Constitution §7), exposing progressive
chunks + attaching sources to the application layer ([03.2 AD-6](03.2_Server_State_Strategy.md)); interruption/
timeout is normalized to the frozen Timeout/partial handling, retaining produced output.

### AD-6 — Best-effort and partial responses are modeled explicitly
Because external sources are best-effort (frozen Vision), the contract/adapters model **partial success**:
the layer surfaces which parts succeeded and which failed, so the UI can render **Partial Failure** rather
than treating the whole response as failed ([03.4](03.4_Data_Fetching_Strategy.md), [03.11](03.11_Error_Boundary_and_Recovery.md)).

### AD-7 — Frontend/backend responsibility split (integration view)
- **Frontend (this layer):** contract typing, request issuance, response validation + mapping, error
  normalization, session/credential *transport* (never storage of raw credentials), and translating
  backend signals into frontend States.
- **Backend (not ours, §6.2):** business logic, AI/grounding, data/persistence, authentication + session
  issuance/validation, retrieval/source generation, external ingestion. The frontend **reflects** backend
  authority; it is never the security or business-logic authority.

## Design Rationale

A single, typed, validated integration layer is the linchpin of a trustworthy data architecture: it makes
the backend boundary explicit and stable (§4.12), turns untrusted remote data into trusted models exactly
once (§4.9, §4.13), and localizes error handling so every failure becomes a recoverable frozen State. Mapping
to domain models insulates the UI from backend shape changes, directly serving progressive decoupling
(§4.14). Concentrating streaming and partial-failure handling here keeps the trust and best-effort promises
consistent across every feature.

## Alternatives Considered

- **Per-component/`fetch`-in-place data access** — rejected: scatters the trust boundary, duplicates error
  handling, couples UI to backend shapes (contra §4.1, §4.3, [02.7](02.7_Module_Dependency_Rules.md)).
- **Passing raw backend shapes to the UI (no adapters)** — rejected: couples UI to backend representation;
  any backend change ripples widely (contra §4.12, §4.14).
- **Trusting responses without validation** — rejected: violates §4.9/§4.13; risks silent corruption of
  financial/AI data.

## Trade-offs

- **Adapter/validation overhead vs. safety:** mapping + validating every response costs some ceremony and
  a little runtime, but buys trust-boundary integrity and decoupling. Accepted (trust-first).
- **Single client vs. per-feature flexibility:** one integration layer is a shared dependency; mitigated by
  a stable contract surface and feature-scoped access patterns.

## Risks

- **Contract drift** between frontend types and backend reality. *Mitigation:* shared contract governance
  (§6.3) + boundary validation catching mismatches fast (§4.13).
- **Bypass** (a component calling the network directly). *Mitigation:* dependency rules + review
  ([02.7](02.7_Module_Dependency_Rules.md)).
- **Credential mishandling.** *Mitigation:* the layer transports session context only; never stores raw
  credentials/keys client-side ([03.6](03.6_Authentication_Architecture.md); privacy/security rules).

## Future Extension Points

- New endpoints/entities add to the contract + adapters behind the stable client surface (§4.14).
- A transport change (e.g. adding real-time subscriptions) is absorbed in the integration layer only.
- Should the stack/contract ever be revisited (the earlier CR-VIS considerations), the integration seam
  bounds the change.
