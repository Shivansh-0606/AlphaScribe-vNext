## Purpose

Define the **dependency rules** that make the M2 architecture enforceable: which directions of dependency
are allowed, which are prohibited, how boundaries are enforced, the import conventions, the coupling rules,
and the extensibility guidelines. These rules are what keep the layered, feature-bounded architecture from
degrading into a coupled monolith over time.

## Scope

**In scope:** allowed/prohibited dependency directions, boundary enforcement, import conventions, coupling
rules, extensibility guidelines. **Out of scope:** implementation, specific lint/tooling configuration
(named as intent, not configured), redefining the layers/features (02, 02.1, 02.2).

## Architectural Decisions

### AD-1 — Allowed dependency directions (inward + upward only)
Two orthogonal ordering rules, both strictly one-directional:

**(a) Layer dependencies point inward** (Clean Architecture, §4.1):
```
Presentation/UI → Feature → Application/Orchestration → Integration → (Foundation/Shared)
```
An outer layer may depend on an inner one; an inner layer must never depend on an outer one. Foundation/
Shared is the innermost/most-stable and depends on nothing application-specific.

**(b) Component composition points upward** ([02.5](02.5_Component_Architecture.md)):
```
Primitives → Foundation → AI → Research → Feature components → Screen compositions
```
A component may compose only **lower** layers; a lower component never imports a higher one.

**(c) Feature dependencies** ([02.2](02.2_Feature_Organization.md)): features depend on **Shared modules**
and on each other **only through shared contracts / public surfaces / routing** — never internals — and the
feature graph is **acyclic**.

### AD-2 — Prohibited dependencies
The following are architectural violations (rejected in review / by enforcement):
- ✗ **Inner → outer** layer dependency (e.g. Integration importing UI; Application importing a feature's UI).
- ✗ **Higher → lower reversed** component import (e.g. a primitive importing a research component).
- ✗ **Feature → another feature's internals** (deep import past its public surface).
- ✗ **Cyclic dependencies** between modules/features/components (any cycle).
- ✗ **Skipping the application layer** (UI/feature reaching directly into Integration/API, bypassing
  use-cases and state ownership).
- ✗ **Importing shadcn primitives directly** in features/screens (must go through the wrapped component
  layer — [02.5](02.5_Component_Architecture.md)).
- ✗ **Design-token or design-system redefinition** downstream (tokens/visuals are Design's; §6.5, §5.3).
- ✗ **Hidden global coupling** (shared mutable singletons used as a back-channel between features — §4.10).

### AD-3 — Boundary enforcement
Boundaries are enforced by construction and by tooling intent (not configured here):
- **Public surfaces:** every feature/shared module is imported only through its declared public entry;
  internals are unreachable across the boundary (§4.12).
- **Automated enforcement (intent):** dependency/boundary linting (e.g. import-boundary rules) and cycle
  detection run as a **CI gate**; a violation fails the build. (Tool selection is a later, governed
  decision — named here as a requirement, not a configuration.)
- **Review gate:** architecture review rejects dependency violations; a genuinely needed new dependency
  direction is an **ADR/CR**, never a silent import (§Constitution §11–§12).

### AD-4 — Import conventions
- **Import via the public surface**, never a deep path into another module's internals (§4.12).
- **Absolute/aliased imports** for cross-module references (a stable, greppable convention — §4.10);
  relative imports stay within a module.
- **Server/client discipline:** respect the rendering seam ([02.6](02.6_UI_Layer_Architecture.md)) —
  client-only concerns are not imported into server-rendered scopes and vice-versa; the boundary is
  explicit.
- **Type-only vs. value imports** are distinguished so contracts can be shared without pulling
  implementation across a boundary (supports low coupling).

### AD-5 — Coupling rules
- **Low coupling, high cohesion** (§4.3, §Constitution §8): related concerns live together; unrelated ones
  are separated; modules depend on **contracts, not internals** (§4.12).
- **Depend on abstractions at boundaries** (§4.1): the Integration layer isolates the backend contract; a
  feature depends on a shared *contract*, not a concrete implementation.
- **Progressive decoupling** (§4.14): every change should leave coupling **lower or equal**, never higher
  without justification; increasing coupling is a reviewable regression.
- **One reason to change** (§4.2 SRP): a module coupled to two unrelated concerns is split.

### AD-6 — Extensibility guidelines
- **Add behind a public surface:** new features/components/shared modules are added by exposing a stable
  interface, leaving existing modules untouched (§4.14) — additive growth.
- **Isolate volatility:** anything likely to change (a dependency, an external contract) sits **behind a
  stable seam** so its change is bounded (§4.12; dependency exit-strategy rule, Constitution §9).
- **Prefer extension over modification** (Open/Closed, §4.2): extend via new implementations behind a
  contract rather than editing a shared one.
- **Govern promotion:** moving a module from feature-local to shared, or changing a public interface, is a
  reviewed (and, if it affects design, CR'd) event — not an ad-hoc refactor.

## Design Rationale

Dependency rules are the *teeth* of the architecture: layering and feature boundaries only hold if the
allowed directions are explicit and enforced. Inward/upward-only dependencies keep the stable core stable
and make change ripple-free (§4.1, §4.12); prohibiting cycles and deep imports prevents the slow slide into
a big ball of mud; and requiring new directions to be ADR/CR'd means coupling is a *decision*, not an
accident. Enforcement in CI plus review makes the rules real rather than aspirational.

## Alternatives Considered

- **Convention-only (no enforcement)** — rejected: conventions without gates erode under deadline pressure;
  the Constitution requires enforceable boundaries (§4.12, §4.14).
- **Allowing feature-to-feature imports "when convenient"** — rejected: this is exactly how coupling webs
  form (contra §4.14).
- **A single shared "utils" free-for-all** — rejected: becomes a coupling hub; shared modules keep small,
  deliberate, contract-based surfaces.

## Trade-offs

- **Enforcement friction vs. long-term health:** boundary linting and public surfaces add friction to
  quick cross-module access, but that friction is the point — it makes the healthy path the easy one.
  Accepted.
- **Abstraction at boundaries vs. directness:** depending on contracts adds indirection; justified by
  isolation and changeability (§4.1, §4.12).

## Risks

- **Enforcement not wired up**, letting violations accrue silently. *Mitigation:* make boundary/cycle
  checks a **CI merge gate** (AD-3); treat a missing gate as a setup defect.
- **"Temporary" violations** becoming permanent. *Mitigation:* any exception is an ADR with a remediation
  plan, not an untracked import.
- **Over-abstraction** in pursuit of decoupling. *Mitigation:* §4.11 simplicity — abstract at real
  boundaries only, justified by a present need.

## Future Extension Points

- The enforcement ruleset extends as new layers/features are added (the directions generalize).
- The Integration-layer seam is the extension point for backend-contract evolution (bounded change).
- As the team scales, the same public-surface rules enable extraction into packages (monorepo) with no
  rule changes (§4.14).
