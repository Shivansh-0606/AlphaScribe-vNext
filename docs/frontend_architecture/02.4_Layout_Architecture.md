## Purpose

Define the **layout hierarchy** of the application: which layouts persist, how layouts nest, the app-shell
architecture, and the responsibilities each layout layer holds. This realizes the frozen layout templates
and the Direction-C experience structurally; it defines **no page designs**.

## Scope

**In scope:** layout hierarchy, persistent layouts, nested layouts, shell architecture, layout
responsibilities. **Out of scope:** designing screens/pages, redesigning the templates (frozen),
implementation.

## Architectural Decisions

### AD-1 — A three-tier layout hierarchy
Layouts nest in three tiers, from most persistent to most specific:

```
Root Shell (persistent across the whole app)
  └── Template Layout (one of the 5 frozen templates, per route group)
        └── Feature / Section Layout (feature-specific structure, e.g. section nav + AI companion)
              └── Route content (feature UI — the "page", not designed here)
```

This maps directly onto the frozen [layout templates](../design/09_Component_Inventory.md#templates) and
the routing groups ([02.3](02.3_Routing_Architecture.md)).

### AD-2 — Persistent layouts preserve state and continuity
The **Root Shell** and appropriate **Template Layouts** persist across navigation (Next.js App Router
preserves layout subtrees). This is an architectural mechanism for the frozen promises of **continuity**
and **never-lose-work** (§6.3; Design Law 6): global chrome, navigation state, and — where applicable —
the AI companion and in-progress context survive route changes rather than remounting.

### AD-3 — The five template layouts (frozen) and their nesting
| Template layout | Persistent regions | Nests |
|-----------------|--------------------|-------|
| **PublicTemplate** | public header, footer | Landing / Auth content |
| **SetupTemplate** | header, footer; **global nav suppressed** | Onboarding & AI Setup content |
| **WorkspaceTemplate** | global header, **global navigation**, footer | Workspace Home / Search / Library / Settings content |
| **ResearchTemplate** | WorkspaceTemplate **+ section nav + AI companion region** | Company Research / Comparison / Learning content |
| **DocumentTemplate** | WorkspaceTemplate **+ linear document + source panel + export** | Report Viewer content |

Templates are **frozen compositions** (Component Inventory); layout architecture places and persists them,
it does not redesign them.

### AD-4 — Shell architecture
The **Root Shell** (root layout) owns the application frame and cross-cutting concerns that must exist
everywhere:
- **Global chrome placement:** header and (where the template calls for it) global navigation — identical
  placement/behavior everywhere (frozen Navigation rule).
- **Accessibility landmarks and skip link:** `banner`, `nav`, `main`, `complementary` (AI companion),
  `contentinfo`; skip-to-content — accessibility by default (§4.6; frozen Accessibility).
- **Global providers (as architecture):** the cross-cutting contexts the app needs (theme/token surface,
  query/data provider, state provider, reduced-motion, observability, error boundary) — *declared as
  responsibilities here; implemented later.*
- **Root error/loading boundaries:** a top-level resilience boundary so no failure escapes unhandled
  (fail-fast for the unexpected; graceful frozen States for the expected — §4.13).

### AD-5 — Layout responsibilities vs. content responsibilities
- **Layouts own structure, persistence, landmarks, and persistent regions** (chrome, nav, section nav,
  companion region, source/export panels) — not business content.
- **Features own the content** rendered into the layout's slots (§4.5).
- **The AI companion region** is a persistent layout concern in ResearchTemplate (a non-modal companion
  that *reflows*, not overlaps, per Direction C); its *contents/behavior* are the AI feature's, its
  *placement/persistence* are the layout's.
- **Responsive adaptation** of layouts follows the frozen [Responsive
  guide](../experience_design/engineering_handoff/04_Responsive_Implementation_Guide.md): the same
  structure adapts density (rail → condensed → drawer), never losing destinations.

## Design Rationale

A persistent, nested layout hierarchy is the structural embodiment of the frozen templates and Direction
C's "living workspace": persistent shells give continuity and preserve work (§6.3) at the framework level
rather than by manual effort; separating layout structure from feature content keeps both cohesive and
independently changeable (§4.3, §4.5); and centralizing landmarks/skip-link in the shell makes accessibility
the default (§4.6).

## Alternatives Considered

- **Per-page full layouts (no shared shell)** — rejected: remounts chrome and loses state on every
  navigation (breaks continuity/never-lose-work), duplicates structure (contra §4.3, §6.3).
- **A single monolithic layout with conditional regions** — rejected: low cohesion, hard to reason about;
  the five frozen templates already delineate the right seams.
- **Companion as an overlay outside the layout tree** — rejected: it must persist and reflow with content
  per Direction C; it belongs in the ResearchTemplate layout.

## Trade-offs

- **Persistent shells vs. memory/coupling:** persistent layouts hold state across navigation (memory cost,
  care needed to avoid stale state) but deliver continuity and performance. Accepted, with explicit state
  ownership at the application layer.
- **Layout/content separation vs. indirection:** slotting content into layouts adds a seam; justified by
  cohesion and reuse.

## Risks

- **State leakage in persistent layouts** (stale context across features). *Mitigation:* explicit state
  ownership + scoping at the application layer ([02.6](02.6_UI_Layer_Architecture.md)); reset on genuine
  context change.
- **Landmark/heading errors** at layout seams. *Mitigation:* shell owns landmarks; Design QA a11y pass.
- **Companion region overlapping content** on desktop. *Mitigation:* reflow rule (Direction C) verified
  responsively.

## Future Extension Points

- New template families (should a future roadmap surface need one) attach as new template layouts under
  the root shell — additive (§4.14).
- Additional persistent regions (e.g. a future global notification center, if approved by CR) attach at
  the shell without disturbing feature content.
