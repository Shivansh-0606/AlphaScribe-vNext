## Purpose

Define the **frontend authorization architecture**: the access boundaries the frontend reflects (what a
user may reach or do), how they are enforced at route/feature/component level, and how denied access
recovers — with the backend as the authoritative enforcer. Authorization for the MVP is deliberately
minimal (authenticated + valid AI access); no roles/features are invented.

## Scope

**In scope:** frontend authorization boundaries, enforcement points, the AI-access gate, recovery from
denial. **Out of scope:** backend authorization enforcement (authoritative, §6.2); authentication
([03.6](03.6_Authentication_Architecture.md)); inventing roles/permissions beyond the frozen baseline;
implementation.

## Architectural Decisions

### AD-1 — The backend is the authorization authority; the frontend reflects it
Authorization is **enforced by the backend** (§6.2): the frontend **never** grants access the backend would
deny, and treats a protected action's true permissibility as backend-authoritative. The frontend's role is
to **reflect** permissions — showing, enabling, or gating affordances — and to route denied access to a
recoverable state. **Frontend gating is UX, not security** (§4.13: never trust the client as the boundary).

### AD-2 — MVP authorization boundaries (no invented scope)
The frozen product defines a **minimal** authorization surface; the frontend models exactly this and no
more:
1. **Authenticated** — a valid session is required for all protected destinations (the login wall,
   [03.6](03.6_Authentication_Architecture.md); handled as Authentication Required).
2. **Valid AI access** — AI-bearing capabilities (copilot, summaries, filing analysis) require **validated
   AI access** (Managed AI or a validated BYOK key). Without it, the frontend surfaces the frozen
   **Permission Denied** state with a recoverable path to **AI Setup** — never a hard stop (frozen States;
   `AIAccessSelector`).

**No roles, tiers, org permissions, or RBAC exist in the MVP** — none are invented here (that would breach
scope). Richer authorization is a future extension (below), gated by product decision.

### AD-3 — Enforcement points: route → feature → component
Authorization is reflected at layered boundaries (defense in depth on the client, all subordinate to the
backend):
- **Route boundary** ([02.3](02.3_Routing_Architecture.md)): access-gated destinations resolve to
  Authentication Required / Permission Denied with recovery — the primary gate.
- **Feature boundary:** a feature reflects access when deciding what its surface offers (e.g. AI features
  render their "access needed" state when AI access is absent).
- **Component/affordance level:** individual affordances are enabled/disabled/hidden per access, always with
  a non-color, explained state (never a dead, unexplained control — frozen a11y/States).
The backend independently enforces every protected operation regardless of these client reflections.

### AD-4 — Denial always recovers (never a dead end)
Per the frozen **Permission Denied** and recovery philosophy (Design §20, Law 13): a denied action shows
*what* is restricted and a *clear path forward* (e.g. "validate AI access to continue" → AI Setup),
preserving the user's context and work. Denial is never a hard stop or lost work.

### AD-5 — Access status is derived server state
"Is AI access valid?" / "Am I authorized for X?" are **backend-authoritative, derived server state** (via
the session/identity + AI-access-status queries), not duplicated client flags ([03 AD-1](03_Data_and_State_Architecture.md)).
The UI derives affordance-gating from this single source.

## Design Rationale

Keeping the backend authoritative and the frontend reflective prevents the frontend from becoming a false
security boundary while still delivering a clear, accessible UX for access limits. Modeling only the frozen
authorization surface (authenticated + AI access) keeps the architecture faithful to scope. Layered
reflection (route/feature/component) makes gating consistent and predictable, and the always-recover rule
upholds the product's "never trap the user / never lose work" guarantees.

## Alternatives Considered

- **Client-enforced authorization as the security boundary** — rejected: the client is never trustworthy as
  the enforcer (§4.13); the backend enforces, the frontend reflects.
- **Introducing roles/RBAC now** — rejected: not in the frozen scope; inventing it would breach the
  milestone's "do not invent features" constraint (would require a CR).
- **Hard-stopping on missing AI access** — rejected: violates the recovery/never-trap principle (frozen
  §20, Law 13); a recoverable Permission Denied is required.

## Trade-offs

- **Backend-authoritative checks vs. instant client gating:** deriving access from the backend costs a
  round-trip but is correct/secure; mitigated by caching access status. Client gating remains as UX only.
- **Minimal MVP authorization vs. future flexibility:** modeling only the frozen surface is simpler now;
  richer authz is a clean future extension (AD-2, below).

## Risks

- **Client gating mistaken for security.** *Mitigation:* AD-1 — backend enforces every protected op;
  client gating is UX; fail-fast if the client ever relies on itself as the boundary.
- **Denied actions dead-ending.** *Mitigation:* always-recover rule (AD-4) + Permission Denied State + QA.
- **Access-status drift** (client flag vs. backend). *Mitigation:* access as derived server state (AD-5).

## Future Extension Points

- Should the roadmap introduce tiers/teams/organization accounts (Version 2.0 Collaboration) or richer
  permissions, an **RBAC/permission model** attaches at these same enforcement points via a product/design
  CR — additively, without restructuring (§4.14).
- Additional AI-access modes extend the AI-access gate without changing the boundary model.
