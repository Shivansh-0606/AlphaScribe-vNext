## Purpose

Define the **project-organization philosophy**, the **responsibilities of each directory**, the **package
boundaries** between modules, and the **ownership rules** — so that where code lives, and what may live
there, is unambiguous. This is an architectural model of structure and responsibility; it **does not
create actual files or scaffolding**.

## Scope

**In scope:** organization philosophy, directory responsibilities (as a reference model), package
boundaries, ownership rules. **Out of scope:** creating application files/folders (Constitution §2);
implementation; the routing/layout/component detail delegated to 02.3–02.6.

## Architectural Decisions

### AD-1 — Feature-first, layered organization
Top-level structure is organized **by feature and by architectural layer**, not by technical type
(§4.5). A feature's concerns are **co-located** behind a public surface; cross-cutting capabilities live
in shared/foundation areas.

### AD-2 — Reference directory model (responsibilities, not scaffolding)
The following is an **architectural reference model** describing directory *responsibilities*. It is
guidance for Engineering; Engineering may adapt names, not intent. **No files are created by this
document.**

```
(app entry)         Route composition only — thin route segments that compose layouts + feature UI.
                    Owns no business logic. (02.3, 02.4)
(features)          One module per frozen IA domain (Company Research, Comparison, Learning,
                    Research Library, Workspace Home, Account & AI Setup). Each exposes a small
                    PUBLIC surface; everything else is internal/private. (02.2)
  <feature>/
    (public surface)    the only sanctioned entry point for other modules
    (ui)                feature-specific presentation (composes design-system components)
    (application)       feature behavior: use-cases, client-state, data hooks (architecture only)
    (integration)       feature-scoped API-contract access + validation (if any)
    (internal)          private helpers/types — never imported across the feature boundary
(components)        The design-system component layer: wrapped shadcn primitives + foundation/AI/
                    research components from the frozen handoff. Presentational; no feature logic. (02.5)
(lib / foundation)  Cross-cutting, app-agnostic capabilities depended on by all, depending on none:
                    design-token consumption, shared types, utilities, accessibility harness,
                    observability, error/fail-fast primitives, motion vocabulary.
(integration/api)   The typed API-contract client + adapters + Zod validation (the trust boundary). (§6)
(styles)            Global styles + token declarations (consumes frozen tokens; never redefines them).
(public assets)     Exported icons/illustrations/logo per the frozen Asset Export Standards.
```

### AD-3 — Package boundaries via public surfaces
Every feature and shared module has an explicit **public surface**; its internals are private and may not
be imported across its boundary (§4.12). Modules depend on each other's *contracts*, never internals.

### AD-4 — Co-location and proximity
A change to one feature should touch (ideally) one module. Concerns that change together live together;
concerns that change independently are separated (§4.3 high cohesion / low coupling).

## Ownership Rules

| Area | Owns it | Notes |
|------|---------|-------|
| Route composition (app entry) | Frontend Architecture (structure) → Engineering (build) | thin; no logic |
| Feature modules | Feature owners (Engineering) within Architecture's boundaries | one per IA domain |
| Design-system components | **Design** (visuals/tokens) · **Architecture** (layering/consumption) · **Engineering** (implementation) | §6.5 |
| Foundation/shared | Frontend Architecture (contract) → Engineering (build) | app-agnostic, stable |
| Integration/API client | Shared frontend/backend (contract) → Engineering (build) | typed + validated (§6) |
| Styles/tokens | **Design** (token values) — consumed here, never modified | §5.3, §6.5 |

**Rule:** no module owns another module's internals; token values are owned by Design and changed only by
CR.

## Design Rationale

Feature-first + layered structure keeps a growing codebase legible and changeable (§4.5, §4.14): a new
engineer finds a feature's concerns in one place, and a change stays local. Public surfaces make the
system's seams explicit and stable (§4.12), which is what lets it scale to hundreds of screens without a
coupling web. Describing structure as *responsibilities* (not created files) keeps this milestone
architectural, per the Constitution.

## Alternatives Considered

- **Type-first structure** (all components/hooks/styles grouped by kind) — rejected: scatters features,
  raises coupling, poor scalability (§4.5).
- **Flat structure** (no module boundaries) — rejected: no seams, unbounded coupling, unmaintainable at
  scale (§4.12).
- **Monorepo package-per-feature** — deferred as a future option (see Extension Points); unnecessary
  overhead for the current scope, but the public-surface model makes it a low-friction future step.

## Trade-offs

- **Structure discipline vs. initial friction:** public surfaces and layer separation add ceremony but
  prevent the far costlier entropy of an unbounded structure. Accepted.
- **Co-location vs. some duplication:** occasionally a small shared concern is duplicated rather than
  prematurely centralized; centralization happens when a real, repeated need appears (§4.11 YAGNI).

## Risks

- **Boundary erosion** (deep imports) collapsing the structure into a monolith. *Mitigation:* import
  conventions + enforcement in [02.7](02.7_Module_Dependency_Rules.md).
- **Over-nesting** harming DX. *Mitigation:* keep the reference model shallow; nest only when a module
  genuinely needs it (§4.11).

## Future Extension Points

- Promote a shared concern to the foundation layer when a repeated cross-feature need is proven.
- Extract a feature into its own package (monorepo) if team scale warrants — the public-surface model
  makes this additive (§4.14).
- New IA domains slot in as new feature modules with no change to the reference model.
