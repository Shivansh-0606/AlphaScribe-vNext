## Purpose

Provide the **single, definitive reference for where every category of frontend state belongs** — its source
of truth, architectural owner, lifetime, and its persistence, synchronization, and recovery expectations.
The objective is absolute: **an engineer should never have to guess where a piece of state belongs.** This
document consolidates, in one matrix, the ownership rules already decided across the Milestone 3 package; it
changes none of them.

## Scope

**In scope:** a comprehensive ownership matrix over every major frontend state category, plus a placement
decision guide for new state. **Out of scope:** implementation, and any new ownership rule (this is a
consolidation, not a redesign).

## Dependencies

[03 Data & State](03_Data_and_State_Architecture.md) (the five-category taxonomy — the backbone of this
matrix); [03.1](03.1_State_Management_Strategy.md)–[03.13](03.13_AI_Streaming_Lifecycle_Architecture.md)
(each category's authoritative treatment); [Constitution](01_Frontend_Architecture_Constitution.md) §4.10
(single ownership), §4.12, §6.3; frozen [States](../design/13_States.md), Law 6.

## Architectural Principles

1. **One datum, one owner.** Every category resolves to exactly one of the five taxonomy homes (server /
   client / form / URL / derived) — the matrix never assigns two authorities to one datum ([03 AD-1](03_Data_and_State_Architecture.md)).
2. **Server is authoritative for anything it owns;** the client holds working/derived copies only ([03.2](03.2_Server_State_Strategy.md)).
3. **Derived is computed, never stored** — loading/error/validation/derived views have no independent home
   ([03.10](03.10_Data_Flow_Principles.md)).
4. **Persistence, synchronization, and recovery are expectations of the owner** — not separate stores.

## The Matrix

> **Taxonomy legend** (owner column): **Server** = backend-owned, cached via TanStack Query (Application
> layer). **Client** = UI-owned via Zustand (Application layer, feature-scoped). **Form** = React Hook Form.
> **URL** = App Router. **Derived** = computed at read time (no store). **Local** = component-local React
> state. These are the [03](03_Data_and_State_Architecture.md) categories; every row maps to one.

**Cross-category notes:**
- Rows 4/15 (Authentication/Session) and 5 (Authorization) are all **backend-authoritative, derived server
  state** — the frontend reflects, never owns, them ([03.6](03.6_Authentication_Architecture.md)/[03.7](03.7_Authorization_Architecture.md)).
- Rows 13/14/10 (Loading/Error/Validation) are **derived** — never stored; they are read-time reflections of
  a server-state query status or a schema check.
- Rows 18/19 (Persistent/Local preferences) describe **persistence expectations**, mapped back to a real
  owner — they are not a new store.
- Row 20 (Feature state) is a **composition** — it resolves into the specific categories its data belongs to.

## Placement Decision Guide (so no one guesses)

To place any new piece of state, answer in order — the first "yes" is its home:

1. **Could the backend own or persist it?** → **Server state** (Query). *(the primary test — [03 AD-2](03_Data_and_State_Architecture.md))*
2. **Is it in-progress input in a form until submit?** → **Form state** (RHF).
3. **Should it be shareable / deep-linkable / survive reload via the address?** → **URL state** (Router).
4. **Can it be computed from existing state?** → **Derived** (compute at read time — do **not** store).
5. **Is it UI/ephemeral with no server home, needed across components/routes?** → **Client (UI) state** (Zustand, feature-scoped).
6. **Is it purely local to one component?** → **Local** component state.

If a datum seems to need two homes, it does not — split it: its **truth** goes to one owner, and any other
view of it is **derived** (§4.10, "one datum, one owner"). Backend-authoritative concerns (auth, access,
session) are always **reflected**, never owned.

## Responsibilities

| Concern | Owner |
|---------|-------|
| Keeping this matrix the single ownership reference, consistent with 03.1–03.13 | **Frontend Architecture** |
| Placing new state per the decision guide; never inventing a home | **Frontend Engineering** (within these rules) |
| Backend authority for server/auth/session/authorization data | **Backend** (§6.2) |

## Trade-offs

- **A single large matrix vs. per-category docs:** the matrix duplicates summaries that live in 03.1–03.13,
  but the consolidated reference is worth the small redundancy — it is the "never guess" artifact. Backward
  traceability is preserved via per-row links.
- **Fine-grained categories vs. the five-home taxonomy:** naming 20 categories risks implying 20 stores;
  mitigated by mapping every row explicitly back to one of the five homes.

## Risks

- **Drift** between this matrix and the source docs. *Mitigation:* the matrix consolidates (does not
  redefine); any ownership change is made in the owning doc first, then reflected here, under governance.
- **Misreading a derived row as a store.** *Mitigation:* explicit "Derived / not stored" language + the
  decision guide.

## Future Extension Points

- New categories (e.g. offline write-queue state, cross-device preferences, real-time presence) are added as
  rows mapped to an owner via the decision guide — additive, no taxonomy change (§4.14).
- If a future roadmap feature makes a currently-client datum server-owned (e.g. cross-device preferences),
  the row moves owners via a governed change, not an ad-hoc copy.
