## Purpose

Define the **environment-configuration strategy** for the frontend: how configuration is structured,
validated, separated by environment, and — critically — how the **public/secret boundary** is enforced so
no secret ever reaches the client. It defines a **strategy**, not config files, values, or CI/CD (excluded).

## Scope

**In scope:** the configuration model (config as validated data), environment separation, the public/secret
boundary, and startup validation. **Out of scope:** actual config values/files, secret management systems,
CI/CD, and backend/runtime operations (excluded). BYOK user keys are covered by [03.6](03.6_Authentication_Architecture.md)/[03.8](03.8_Form_Architecture.md),
not config.

## Dependencies

[Constitution](01_Frontend_Architecture_Constitution.md) §4.9 (Type Safety), §4.10 (Explicitness), §4.13
(Fail Fast), §6 (Boundaries); [M3 03.6 Authentication](03.6_Authentication_Architecture.md), [03.9 Validation](03.9_Validation_Strategy.md);
frozen privacy/security rules, login-wall auth (project guide).

## Architectural Principles / Decisions

### AD-1 — Configuration is explicit, typed, and validated data
Configuration is treated as **data, not scattered literals**: it is **typed and validated** (via the
validation strategy, [03.9](03.9_Validation_Strategy.md)) so misconfiguration is caught, not silently
tolerated (§4.9, §4.10). No behavior branches on undocumented ad-hoc environment reads.

### AD-2 — The public/secret boundary is absolute
The single most important rule: **secrets never reach the client.** Only **non-sensitive, public runtime
configuration** (e.g. the API base location, public feature toggles, public identifiers) may be present in
the frontend; **secrets** (credentials, session-signing material, private keys, third-party secret keys)
live **server-side only** and are never bundled, logged, or exposed (§6; frozen security/privacy). This
boundary is explicit and reviewed.

### AD-3 — User-provided AI keys are runtime input, not configuration
BYOK AI keys are **user-provided at runtime** and handled per [03.6](03.6_Authentication_Architecture.md)/[03.8](03.8_Form_Architecture.md)
(transient, transmitted to the backend, **never stored client-side, never logged, never in config or URLs**).
They are **not** environment configuration and must never be treated as such.

### AD-4 — Environment separation is a first-class concern
Configuration distinguishes **environments** (e.g. local/development, staging/preview, production) as a
concept, so behavior and endpoints are environment-appropriate without code changes. The **set of config
keys is identical across environments**; only values differ — preventing environment-specific code paths
(§4.10). *(How environments are provisioned is an ops/CI concern, out of scope; the strategy fixes the
separation.)*

### AD-5 — Configuration is validated at startup (fail fast)
Required configuration is **validated when the application initializes**: missing or malformed config
**fails fast** with a clear diagnostic ([03.11](03.11_Error_Boundary_and_Recovery.md), §4.13) rather than
surfacing as a confusing runtime error later. A misconfigured app should refuse to run incorrectly, not run
wrongly.

### AD-6 — Configuration is centralized and consumed via a typed contract
Configuration is accessed through a **single typed contract** (foundation layer, [02.1](02.1_Project_Structure.md)),
not read ad-hoc across components — so its shape is one source of truth, its consumption is greppable, and
the public/secret boundary is enforced in one place (§4.12).

## Design Rationale

Treating configuration as typed, validated, centralized data with an absolute public/secret boundary and
startup validation prevents the two most damaging config failures: a **secret leaking into the client** and a
**misconfiguration running silently wrong**. Environment separation with an identical key set avoids
environment-specific code drift. Keeping BYOK keys explicitly out of config protects the product's security
posture. This is strategy only — Engineering wires the concrete mechanism.

## Alternatives Considered

- **Scattered `process.env`-style reads** — rejected: untyped, unvalidated, easy to leak secrets or
  misconfigure (contra §4.9/§4.10); config is centralized and typed.
- **Secrets in client config "for convenience"** — rejected categorically: violates the security boundary
  (AD-2).
- **Environment-specific code branches** — rejected: identical key set + values-only differences avoid drift
  (AD-4).

## Trade-offs

- **Centralized typed config vs. quick inline reads:** a config contract is more ceremony than an inline
  env read, but it enforces the secret boundary and validation. Accepted (security-first).
- **Startup validation vs. lenient boot:** failing fast on bad config is stricter but prevents silent
  misbehavior. Accepted.

## Risks

- **Secret leakage into the client bundle.** *Mitigation:* AD-2 boundary + review; only public config
  client-side.
- **Silent misconfiguration.** *Mitigation:* AD-5 startup validation (fail fast).
- **BYOK key mishandling as config.** *Mitigation:* AD-3 — keys are runtime input, never config.

## Future Extension Points

- Concrete config mechanisms and secret management are Engineering/ops decisions within this strategy (out of
  scope here).
- Runtime feature flags (if introduced by product via CR) extend the public-config model.
- Multi-region/locale config extends AD-4 when localization ([04.9](04.9_Internationalization_Readiness.md))
  is adopted.
