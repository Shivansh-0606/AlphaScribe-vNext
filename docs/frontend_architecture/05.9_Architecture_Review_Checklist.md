## Purpose

Provide a **single, repeatable checklist** for reviewing that implementation (and architecture changes)
**conform to the frozen Frontend Architecture**. It consolidates the review gates distributed across M1–M4
into one reviewer-usable list, so conformance is verifiable rather than subjective. It defines a **process
artifact**, not architecture.

## Scope

**In scope:** the architecture-conformance review checklist and how it is used in the review workflow. **Out
of scope:** correctness/behavior review depth beyond architecture (engineering review), Design QA (frozen
Experience process), and implementation.

## Architectural Decisions

### AD-1 — One checklist, applied at every architecture-affecting review
The checklist is applied when reviewing implementation of, or changes to, the architecture — alongside the
engineering (correctness) and Design QA (fidelity) tracks ([05.7 AD-3](05.7_Frontend_Governance.md)). It is
part of the merge gate, not a courtesy.

### AD-2 — The conformance checklist
A reviewer answers each; a material "no" blocks the change.

**Structure & boundaries (M2)**
- ☐ Dependencies point **inward/upward only**; no cycles; no cross-feature deep imports ([02.7](02.7_Module_Dependency_Rules.md)).
- ☐ Modules communicate through **public surfaces**; internals not reached across boundaries ([02.2](02.2_Feature_Organization.md), [02.5](02.5_Component_Architecture.md)).
- ☐ Features trace to a **frozen IA domain**; no invented feature/scope ([02.2](02.2_Feature_Organization.md)).
- ☐ Routes are **thin** and realize the frozen Navigation only; no new destinations ([02.3](02.3_Routing_Architecture.md)).
- ☐ Server/client boundary is deliberate (server-first where apt) ([02.6](02.6_UI_Layer_Architecture.md)).

**Data & state (M3)**
- ☐ State placed per the **[Data Ownership Matrix](03.14_Data_Ownership_Matrix.md)**; **no duplicated state**.
- ☐ Server data via Query, client via Zustand, forms via RHF; derived **computed, not stored**.
- ☐ All backend access via the **integration layer**; responses **validated (Zod)** at the boundary ([03.3](03.3_API_Layer_Architecture.md), [03.9](03.9_Validation_Strategy.md)).
- ☐ **Never-lose-work** upheld across error/nav/timeout; Resume Session intact ([03.11](03.11_Error_Boundary_and_Recovery.md)).
- ☐ AI streaming: partial retained on interrupt; **every claim sourced**; AI distinct from source ([03.13](03.13_AI_Streaming_Lifecycle_Architecture.md)).
- ☐ **Fail fast** on unexpected/invalid data; expected [States](../design/13_States.md) handled gracefully.

**Experience (M4)**
- ☐ **Tokens only** — no raw hex/px/ms/z-index ([04.2](04.2_Design_Token_Consumption_Strategy.md)).
- ☐ shadcn primitives **wrapped**, not used raw; variants/states match the design 1:1 ([04.1](04.1_Design_System_Integration.md)).
- ☐ Single **theme**; no toggle/dark mode introduced ([04.3](04.3_Theme_Architecture.md)).
- ☐ **Responsive**: one adaptive structure; destination parity; no horizontal scroll; 200%/320px reflow ([04.4](04.4_Responsive_Architecture.md)).
- ☐ **Accessibility (WCAG AA)**: keyboard, focus, roles/names/states, no color-only, reduced-motion — automated **and** manual pass ([04.5](04.5_Accessibility_Architecture.md)).
- ☐ **Motion**: token-driven, communicative (not decorative), reduced-motion-safe ([04.6](04.6_Motion_Architecture.md)).
- ☐ Frozen **States** rendered consistently and recoverably ([04.7](04.7_Loading_Empty_and_Error_Experience.md)).
- ☐ **Performance**: server-first/islands, code-split, within budgets, perceived-performance patterns ([04.8](04.8_Performance_Architecture.md)).

**Engineering readiness (M5) & governance**
- ☐ Trust-critical paths **tested**; frozen States + a11y covered ([05.1](05.1_Testing_Architecture.md)).
- ☐ **No secrets client-side**; config typed/validated ([05.4](05.4_Environment_Configuration.md)).
- ☐ New/changed dependency has a **lifecycle plan** and is isolated behind a seam ([05.5](05.5_Dependency_Guidelines.md)).
- ☐ **Conventions** followed (naming = design/vocabulary, imports, typing) ([05.8](05.8_Engineering_Conventions.md)).
- ☐ **Docs updated** with the change; significant decision has an **ADR**; frozen-scope change went via **CR** ([05.2](05.2_Documentation_Standards.md), [05.6](05.6_Architecture_Decision_Record_Index.md), [05.7](05.7_Frontend_Governance.md)).
- ☐ Observability hooks present on trust-critical/failure paths; privacy respected ([05.3](05.3_Logging_and_Observability_Hooks.md)).

### AD-3 — Blocking vs. advisory
Violations of **Immutable Laws** (accessibility, never-lose-work, traceability, no-color-only, tokens-only,
no-scope-invention) and **dependency/boundary rules** are **blocking**. Style/advisory items are noted but
non-blocking. Sign-off is recorded ([05.7](05.7_Frontend_Governance.md)).

## Design Rationale

Consolidating the review gates that are otherwise scattered across five milestones into one reviewer-usable
checklist is what makes architectural conformance **actually enforced** rather than aspirational. It gives
every reviewer the same objective basis, front-loads the Immutable-Law and trust-critical checks, and ties
each item back to its authoritative document — making review fast, consistent, and traceable.

## Alternatives Considered

- **Relying on reviewers' memory of five milestones** — rejected: inconsistent; a single checklist
  standardizes review.
- **Merging this into Design QA** — rejected: Design QA covers fidelity; this covers architecture
  conformance; both are needed ([05.7 AD-3](05.7_Frontend_Governance.md)).

## Trade-offs

- **Checklist length vs. thoroughness:** the list is long because the architecture is comprehensive; items
  link to their source for depth without bloating the review. Accepted.
- **Gate friction vs. conformance:** the gate slows merges slightly but prevents architectural drift.
  Accepted.

## Risks

- **Checklist treated as a rubber stamp.** *Mitigation:* blocking items (AD-3) + recorded sign-off; automate
  the mechanical checks (tokens/boundaries/a11y) where feasible.
- **Checklist drifting from the architecture.** *Mitigation:* it links to authoritative docs; updated via
  governance when they change.

## Future Extension Points

- Automate mechanical items (token lint, boundary/cycle lint, axe) so human review focuses on judgment.
- A PR template embeds the checklist; sign-off is captured in the PR.
