## Purpose

Define the **engineering conventions** — the shared, enforceable rules for naming, structure, typing,
imports, and change hygiene — that make the codebase **consistent, readable, and maintainable** as it grows.
These are conventions (rules), not code or a folder structure; they operationalize the Constitution's
Engineering Principles (§8) and the M2 structure/dependency rules.

## Scope

**In scope:** naming, module/public-surface conventions, TypeScript conventions, import conventions, state/
data conventions, and change hygiene (commit/PR expectations). **Out of scope:** implementation code, actual
folder scaffolding, and CI/CD (excluded).

## Architectural Decisions

### AD-1 — Naming reflects meaning and the frozen vocabulary
Names describe **role/meaning**, not appearance or implementation (§4.10). Product and component names use the
**frozen vocabulary verbatim** (Company Research, Research Session, Resume Session, Trusted AI; §15) and the
**design component names 1:1** ([Component Mapping](../experience_design/engineering_handoff/12_Component_Mapping.md),
[02.5](02.5_Component_Architecture.md)). No synonyms; design name = code name.

### AD-2 — Modules communicate through public surfaces
Every feature/shared module exposes a **small, deliberate public surface**; internals are private and
imported only through that surface (§4.12, [02.7](02.7_Module_Dependency_Rules.md)). This convention is what
keeps coupling low as the codebase grows.

### AD-3 — Import conventions
Imports go **through public surfaces**, never deep paths into another module's internals; **absolute/aliased**
imports for cross-module references (greppable, stable), relative within a module; the **server/client
boundary** is respected in imports ([02.6](02.6_UI_Layer_Architecture.md)); **type-only vs. value** imports
are distinguished. Dependency directions follow [02.7](02.7_Module_Dependency_Rules.md) (inward/upward only,
acyclic).

### AD-4 — TypeScript conventions (strong typing at boundaries)
Strong typing is a convention, not a suggestion (§4.9): data crossing boundaries is **typed and validated**
(schemas as the shape source of truth, [03.9](03.9_Validation_Strategy.md)); **no implicit `any` at
boundaries**; illegal states are made unrepresentable where practical; public interfaces are explicitly
typed. Types are part of the interface.

### AD-5 — State, data, and token conventions
State is placed per the **[Data Ownership Matrix](03.14_Data_Ownership_Matrix.md)** decision guide (one datum,
one owner — no duplication); server data via TanStack Query, client via Zustand, forms via RHF, derived
computed. Visual values use **tokens only** ([04.2](04.2_Design_Token_Consumption_Strategy.md)) — no raw
literals. These conventions make the M3/M4 architecture the path of least resistance.

### AD-6 — Change hygiene (readable, reviewable changes)
Changes are **small, cohesive, and reviewable** (§4.11); a change updates its **documentation** in the same
change ([05.2](05.2_Documentation_Standards.md)); commit/PR descriptions state intent and reference the
relevant frozen artifact/ADR/CR for traceability; a change touching the design system or a frozen decision
follows the **CR path** ([05.7](05.7_Frontend_Governance.md)). *(Specific commit-message formats and PR
templates are Engineering's to finalize within these conventions.)*

## Design Rationale

Consistent conventions are what let many engineers produce one coherent codebase over years. Anchoring naming
to the frozen vocabulary and design names removes a whole class of ambiguity and makes design↔code review
trivial; public-surface + import + dependency conventions keep coupling low; strong typing and token/state
conventions make the M3/M4 architecture the easy default; and change hygiene keeps history and docs
trustworthy. These operationalize §8 without prescribing implementation.

## Alternatives Considered

- **Ad-hoc naming/structure per engineer** — rejected: inconsistency and high onboarding cost (contra §8).
- **Deep imports for convenience** — rejected: breaks module boundaries ([02.7](02.7_Module_Dependency_Rules.md)).
- **Loose typing at boundaries** — rejected: forfeits the earliest correctness guarantee (§4.9).

## Trade-offs

- **Convention discipline vs. individual freedom:** shared rules constrain personal style, but consistency
  and readability at scale outweigh it. Accepted.
- **Strong-typing/boundary ceremony vs. speed:** typing and public surfaces add a little friction, repaid in
  safety and maintainability. Accepted.

## Risks

- **Conventions ignored under pressure.** *Mitigation:* review checklist ([05.9](05.9_Architecture_Review_Checklist.md))
  + lint where feasible.
- **Naming drift from the design/vocabulary.** *Mitigation:* AD-1 (1:1 names; frozen vocabulary) + review.
- **Boundary/typing erosion.** *Mitigation:* dependency + type conventions + [02.7](02.7_Module_Dependency_Rules.md) enforcement.

## Future Extension Points

- Lint/format rules and a PR template encode these conventions (Engineering's, within this document).
- Conventions extend to new module types and, if the team scales, to package boundaries (monorepo).
