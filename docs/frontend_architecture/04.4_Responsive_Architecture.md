## Purpose

Define the **responsive architecture** that delivers the frozen [Responsive Behavior](../design/11_Responsive_Behavior.md)
and [Experience Responsive guide](../experience_design/engineering_handoff/04_Responsive_Implementation_Guide.md)
**with one structure that adapts density — never duplicated layouts.** It restates and applies (does not
change) the responsive decisions of [M2 02.4](02.4_Layout_Architecture.md)/[02.6](02.6_UI_Layer_Architecture.md).

## Scope

**In scope:** the responsive delivery model (single adaptive structure), breakpoint/grid consumption,
component adaptation, and the "no architectural duplication" guarantee. **Out of scope:** redesigning
responsive behavior (frozen), per-screen redlines (Experience, pending M2 Phases 3–4), and implementation.

## Architectural Decisions

### AD-1 — One structure, adaptive density (no duplicated layouts)
The governing rule (frozen §18): **structure and destinations are constant across sizes; only presentation
density and arrangement adapt.** The architecture therefore delivers **a single component/layout that
adapts responsively** — **never** separate mobile/desktop components or a parallel mobile product. This is
the "responsive without architectural duplication" guarantee (quality requirement; §4.5).

### AD-2 — Breakpoints and grid are consumed from frozen tokens
Responsive adaptation consumes the frozen breakpoint and grid tokens (`--bp-mobile/tablet/desktop/wide`;
`--grid-columns` 4/8/12; `--reading-max`) via the token layer ([04.2](04.2_Design_Token_Consumption_Strategy.md))
mapped to Tailwind v4 screens. No breakpoint or grid value is invented in components.

### AD-3 — Adaptation is CSS-driven and server-compatible
Responsive adaptation is expressed through **CSS (Tailwind responsive utilities + container queries)**, not
JavaScript viewport branching — so it works with **server rendering** ([04.8](04.8_Performance_Architecture.md),
§7), avoids hydration/layout-shift issues, and needs no client measurement to render the correct layout.
**Container queries** are used where a component's *own context* (not the viewport) should drive its density
(e.g. a card in a reflowing grid).

### AD-4 — Components adapt per the frozen responsive patterns
Adaptation follows the frozen [Experience Responsive guide](../experience_design/engineering_handoff/04_Responsive_Implementation_Guide.md)
patterns (restated, not changed): overlays → sheets/full-screen on mobile; tables → horizontal-scroll or
record-rows (no data dropped); tabs → scroll/picker; navigation → rail/condensed/drawer with **destination
parity**; the AI companion → non-modal desktop drawer that *reflows* → mobile sheet; hover affordances →
tap-to-reveal on touch. Reading measure (`--reading-max`) is preserved at every size.

### AD-5 — Responsive integrity is enforced
The frozen constraints — **destination parity** (no capability lost on any size), **no horizontal page
scroll**, **reflow to 320px and 200% zoom** — are treated as **accessibility+responsive acceptance
criteria** ([04.5](04.5_Accessibility_Architecture.md); Design QA responsive pass), not best-effort.

## Design Rationale

A single adaptive structure is the only way to keep the experience identical across sizes without doubling
the code and inviting drift; CSS/container-query-driven adaptation keeps it server-compatible and
performant. Consuming frozen breakpoint/grid tokens guarantees the layout system matches the design.
Enforcing parity/reflow makes responsive correctness verifiable. Together these deliver the frozen
responsive behavior faithfully and maintainably.

## Alternatives Considered

- **Separate mobile and desktop component trees** — rejected: duplication, drift, double maintenance (contra
  §4.5, the no-duplication requirement).
- **JavaScript viewport branching to choose layouts** — rejected: breaks server rendering, causes layout
  shift/hydration cost (contra §7, §4.7); CSS/container queries are used instead.
- **Dropping content on small screens** — rejected: violates parity/reflow (frozen §18); content reflows,
  never disappears.

## Trade-offs

- **CSS-driven adaptation vs. JS control:** CSS is less imperatively flexible but far more performant and
  SSR-safe; the frozen behavior fits CSS/container queries. Accepted.
- **Container queries vs. viewport-only:** container queries add a modern dependency but correctly scope
  component density; used where context (not viewport) matters.

## Risks

- **Duplicated layouts sneaking in** under deadline. *Mitigation:* AD-1 rule + review; one adaptive
  component.
- **Parity loss / horizontal scroll / zoom clipping.** *Mitigation:* AD-5 acceptance criteria + Design QA
  responsive + a11y passes.
- **Layout shift** from JS-measured responsiveness. *Mitigation:* CSS-first adaptation (AD-3).

## Future Extension Points

- New surface types adopt the single-adaptive-structure model (§4.14).
- Additional breakpoints (if design ever adds one via CR) extend the token set; components consume them with
  no structural change.
