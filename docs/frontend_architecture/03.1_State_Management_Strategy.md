## Purpose

Define the architecture of **client (UI) state** — the ephemeral, session, and interaction state the UI
owns — managed with **Zustand**: what qualifies, how stores are structured and scoped, the state
lifecycle, and the ownership rules that keep client state from duplicating server state.

## Scope

**In scope:** client/UI state ownership, store architecture, scoping, lifecycle, persistence philosophy.
**Out of scope:** server state ([03.2](03.2_Server_State_Strategy.md)), form state ([03.8](03.8_Form_Architecture.md)),
implementation of any store.

## Architectural Decisions

### AD-1 — What qualifies as client (UI) state
Only **UI/ephemeral/session** concerns the backend does not own:
- view/interaction state (AI companion open/collapsed, active section/tab, expanded/collapsed regions);
- transient selection and local filters (e.g. a comparison working-selection, a library filter);
- the **watchlist** grouping (a client-owned list of companies to track — carried forward from the existing
  client watchlist store);
- ephemeral flags (a dismissed inline hint, a transient toggle).

**Explicitly NOT client state:** server data (→ Query, [03.2](03.2_Server_State_Strategy.md)); form values
(→ RHF, [03.8](03.8_Form_Architecture.md)); derived values (computed, [03.10](03.10_Data_Flow_Principles.md));
navigable location (→ URL, [02.3](02.3_Routing_Architecture.md)); theme (fixed single light theme — no
toggle, frozen).

### AD-2 — Feature-scoped, minimal stores
Client state is organized as **small, feature-scoped stores** aligned to the feature boundaries
([02.2](02.2_Feature_Organization.md)); a store exposes a **stable public surface** (§4.12) and holds only
what its feature's UI genuinely needs. Truly global UI state (e.g. companion visibility that spans the
research shell) lives in a small shared store; everything else is feature-local. Stores stay lean —
resisting the "one giant global store" anti-pattern (§4.11).

### AD-3 — Selectors and read discipline
Presentation reads client state through **selectors** (narrow, memoized reads), not by consuming whole
stores — keeping re-renders scoped and coupling low (§4.3). Derived values are computed in selectors, not
stored (§4.10, [03.10](03.10_Data_Flow_Principles.md)).

### AD-4 — State lifecycle
- **Creation:** a store is created for a feature/shell concern with explicit initial state.
- **Scope:** state is scoped to where it is meaningful; context-specific state (e.g. a company's active
  section) resets on genuine context change so stale UI state never bleeds across subjects.
- **Persistence (selective):** most client state is in-memory and ephemeral; a small subset that should
  survive reload within a session persists to **sessionStorage** (the existing `usePersistedState`
  pattern) — e.g. companion collapse preference, non-sensitive filters. **No sensitive research/PII/
  credentials** are persisted client-side (privacy/security). Watchlist persistence follows the existing
  client store's approach.
- **Teardown/reset:** client UI state is cleared on logout/session end alongside cached server state
  ([03.6](03.6_Authentication_Architecture.md)); context-scoped state resets on context change.

### AD-5 — Ownership rules
Client state is owned by the **Application layer** of its feature (bound into the UI, not owned by
presentational components — [02.6](02.6_UI_Layer_Architecture.md)). A store never holds a copy of server
data (AD-1; [03 AD-1](03_Data_and_State_Architecture.md)); if the UI needs server data, it reads it from
Query, not from a mirror in Zustand.

## Design Rationale

Confining Zustand to genuinely UI-owned, ephemeral state — and keeping stores small and feature-scoped —
prevents the two failure modes that plague client state: a bloated global store that couples everything,
and server data duplicated into client state where it drifts from the source of truth. Selectors keep
rendering efficient and coupling low. Selective sessionStorage persistence serves continuity
(never-lose-work at the UI level) without leaking sensitive data.

## Alternatives Considered

- **React Context/`useState` for cross-cutting UI state** — rejected for shared/cross-route UI state:
  prop-drilling/provider sprawl and re-render breadth; Zustand's scoped selectors are cleaner. (Local,
  truly component-local state may still use React state — that is not "client state" in this taxonomy.)
- **One global Zustand store** — rejected: couples unrelated features, grows unbounded (contra §4.11, §4.14).
- **Persisting all client state** — rejected: risks stale UI and, worse, leaking sensitive data; only a
  minimal, non-sensitive subset persists.

## Trade-offs

- **Multiple small stores vs. one:** more stores to track, but each is cohesive and independently
  evolvable (§4.14). Accepted.
- **Selector discipline vs. convenience:** reading via selectors is more deliberate than grabbing the whole
  store, but it bounds re-renders and coupling. Accepted.

## Risks

- **Server data leaking into client state.** *Mitigation:* AD-1/AD-5 + the [03 AD-2](03_Data_and_State_Architecture.md)
  test + dependency review.
- **Store sprawl / global creep.** *Mitigation:* feature-scoping + minimalism (§4.11); review.
- **Sensitive data persisted.** *Mitigation:* explicit persistence allow-list; never persist PII/
  credentials/research bodies.

## Future Extension Points

- New feature UI concerns add their own scoped store behind a public surface (§4.14).
- Cross-device/session UI preferences (if ever wanted) move from sessionStorage to a server-owned
  preference (then they become *server* state) — a governed change, not a client-store expansion.
