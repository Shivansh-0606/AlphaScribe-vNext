## Purpose

Define the **accessibility architecture** that makes **WCAG 2.1 AA the default and enforced** across the
application — the shared accessibility mechanisms every component and screen inherits, and how conformance
is guaranteed rather than hoped for. It delivers the frozen [Accessibility](../design/12_Accessibility.md)
spec and the [Experience Accessibility Implementation guide](../experience_design/engineering_handoff/06_Accessibility_Implementation_Guide.md);
it defines no new accessibility requirements (those are frozen).

## Scope

**In scope:** the accessibility-by-default architecture — shared a11y mechanisms (semantics, focus,
announcements, reduced motion), and the enforcement model (CI + QA). **Out of scope:** restating the frozen
a11y spec in full (linked), and implementation.

## Architectural Decisions

### AD-1 — Accessibility is infrastructure, not a feature (by default)
WCAG 2.1 AA is an **Immutable Law** (Constitution §17, Law 10). The architecture makes the **accessible path
the default path**: accessible semantics, keyboard operability, focus management, and announcements are
**built into the shared component/infrastructure layers**, so a feature is accessible by inheriting them,
not by remembering to add them (§4.6).

### AD-2 — A shared accessibility harness (provided once, inherited everywhere)
The infrastructure provides, once, the cross-cutting a11y mechanisms every surface uses (named as
architecture; not implemented here): a **focus-management** utility (focus trap for modals, return-to-
trigger, focus-to-first-error, route-change focus), a **live-region/announcement** utility (correct
politeness; considerate AI-streaming announcements), a **reduced-motion** signal ([04.6](04.6_Motion_Architecture.md)),
and **visually-hidden/semantic** helpers. These are **foundation-layer** capabilities ([02.1](02.1_Project_Structure.md),
[04](04_Experience_Infrastructure.md)) depended on by all.

### AD-3 — Accessible-by-construction primitives
The wrapped **shadcn primitives** ([04.1](04.1_Design_System_Integration.md)) are chosen and wrapped so they
ship correct roles, names, states, and keyboard behavior; the wrapper's job is to **preserve** those
semantics and bind names/tokens — **never to remove them** (e.g. no `outline:none` without a visible
replacement). Native semantics first; ARIA only to fill genuine gaps (frozen a11y).

### AD-4 — The frozen a11y contract is delivered uniformly
Every component/screen meets the frozen contract ([Accessibility](../design/12_Accessibility.md);
[Experience 06](../experience_design/engineering_handoff/06_Accessibility_Implementation_Guide.md)): full
keyboard operability + logical focus order; correct roles/names/states + landmarks; **AA contrast** (from the
frozen tokens — never re-tuned, [04.2](04.2_Design_Token_Consumption_Strategy.md)); **no meaning by color
alone**; announcements at correct politeness; **reduced motion** honored losslessly; **reflow to 320px /
200% zoom**; **≥44px touch targets**. These are consumed from the frozen spec, not redefined.

### AD-5 — Accessibility is enforced as a merge gate
Conformance is **enforced, not trusted** (§4.13): automated checks (axe / a11y lint) run in **CI as a merge
gate**; component tests assert keyboard interaction and role/name/state; and the Design QA manual pass
(keyboard-only, screen-reader, contrast/color-blind, zoom/reflow, reduced-motion) is required
([Design QA](../experience_design/engineering_handoff/10_Design_QA_Process.md)). **No component or screen
merges with accessibility deferred.**

### AD-6 — Journey-level accessibility is the success measure
The success bar (frozen Experience 06): a **keyboard-only and screen-reader-only user can complete every
approved journey (J-01…J-06)** with no dead ends and no lost work. Accessibility is validated at the journey
level, not just the component level.

## Design Rationale

Accessibility only survives a multi-year, multi-engineer product if it is **structural and enforced**;
retrofitting always leaves gaps. Providing the a11y harness once and inheriting it, choosing
accessible-by-construction primitives, and gating merges on automated + manual conformance makes AA the
default outcome rather than an aspiration — satisfying the Immutable Law and the "enforce accessibility by
default" quality requirement.

## Alternatives Considered

- **Accessibility as a QA-only, end-of-cycle pass** — rejected: too late and incomplete; a11y is built into
  the foundation and gated continuously (§4.6, §4.13).
- **Per-component bespoke a11y** — rejected: inconsistent and error-prone; a shared harness + accessible
  primitives standardize it.
- **Relying on automated axe checks alone** — rejected: automation catches a minority; the manual keyboard/
  SR pass is required (frozen Experience 06 / Design QA).

## Trade-offs

- **Harness + enforcement overhead vs. guaranteed conformance:** the a11y harness and CI gates add work, but
  they are the only reliable path to AA at scale. Accepted (Immutable Law).
- **Native-first semantics vs. custom control flexibility:** preferring native/accessible primitives limits
  some custom behaviors, but those behaviors rarely justify losing accessibility.

## Risks

- **A11y regressions across many screens.** *Mitigation:* CI axe gate + per-component keyboard/SR tests +
  Design QA (AD-5).
- **Wrapper removing primitive semantics.** *Mitigation:* AD-3 (preserve, never remove); review.
- **Contrast broken by an off-token color.** *Mitigation:* token consumption ([04.2](04.2_Design_Token_Consumption_Strategy.md));
  contrast is frozen and never re-tuned.

## Future Extension Points

- Raising the target beyond AA (e.g. AAA where feasible) is a governed enhancement building on this
  infrastructure.
- Localization ([04.9](04.9_Internationalization_Readiness.md)) interacts with a11y (lang attributes,
  translated names) — the harness accommodates it.
- Additional assistive-tech testing (more SRs/devices) extends AD-5's matrix without architectural change.
