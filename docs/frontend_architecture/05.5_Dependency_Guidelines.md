## Purpose

Define the **operational governance of frontend dependencies** — the rules and process for introducing,
evaluating, upgrading, and removing them — operationalizing the Constitution's Dependency Philosophy (§9)
for the engineering team. It **changes no dependency decision**; it makes §9 executable.

## Scope

**In scope:** dependency governance — the fixed approved stack, the lifecycle-plan requirement, evaluation
criteria, upgrade and removal process. **Out of scope:** adding dependencies, changing the approved stack
(CR-only), and implementation.

## Dependencies

[Constitution](01_Frontend_Architecture_Constitution.md) §4.11 (Simplicity), §4.12 (Stable Interfaces),
§4.14 (Progressive Decoupling), §5.4 (approved stack), §9 (Dependency Philosophy — the lifecycle rule);

## Architectural Decisions

### AD-1 — The approved stack is fixed; the toolkit is the default
The approved stack (§5.4: Next.js 15, React 19, TypeScript, Tailwind CSS v4, shadcn/ui, Motion, Zustand,
TanStack Query, React Hook Form, Zod) is the **default toolkit** and is **fixed** — a change or a new **core**
technology requires a **CR** (§5.4). Engineers reach for the approved stack, the platform, or a few lines of
first-party code before anything new (§4.11).

### AD-2 — Every dependency has a lifecycle plan (the §9 governing rule)
No dependency is adopted without answering the four §9 questions, **recorded** (as an ADR for significant
dependencies — [05.6](05.6_Architecture_Decision_Record_Index.md)):
- **Justification** — why it is needed, and why nothing existing/platform/first-party serves the need.
- **Maintenance strategy** — how it is kept current/secure, and who watches its health.
- **Replacement strategy** — what it would be replaced with if it fails us.
- **Exit strategy** — the **stable seam** ([§4.12](01_Frontend_Architecture_Constitution.md)) that isolates
  it so removal is bounded, not a rewrite.
A dependency with no exit is not adopted (§9).

### AD-3 — Evaluation criteria
A candidate dependency is assessed on: **necessity** (real, unserved need), **fit** with the architecture and
stack, **maintenance health/longevity**, **security posture**, **bundle/performance cost** (against budgets,
[04.8](04.8_Performance_Architecture.md)), **accessibility quality** (for anything touching UI,
[04.5](04.5_Accessibility_Architecture.md)), **license**, and **cost of removal**. A dependency that fails
accessibility or materially harms performance is rejected regardless of convenience.

### AD-4 — Isolate every dependency behind a seam
Consistent with [02.7](02.7_Module_Dependency_Rules.md)/§4.14: a dependency is **wrapped/isolated behind a
stable interface** (as shadcn is wrapped, [04.1](04.1_Design_System_Integration.md)) so its change or removal
is a **localized** change. Dependencies do not spread unmediated through the codebase.

### AD-5 — Upgrades are deliberate and governed
Upgrades are **reviewed, not automatic**: security patches are prioritized; major/breaking or strategy-
affecting upgrades are **ADR/CR events**; the surface is kept current enough to stay supported, conservative
enough to stay stable (§9). Core-stack version changes follow the stack-change CR path (AD-1).

### AD-6 — Removal is preferred and follows a deprecation path
**Deletion over accretion** (§4.11, §9): unused/superseded/no-longer-justified dependencies are removed via
**deprecate → confirm no consumers → migrate → remove**, tracked so nothing breaks silently. The dependency
surface is kept lean; every dependency must continue to earn its place.

## Design Rationale

Operationalizing §9 turns dependency discipline from a principle into a repeatable process: the fixed stack
plus the lifecycle-plan requirement means the team never accretes lock-in it cannot escape, and isolation
behind seams keeps the architecture free to evolve (§4.14). Governing upgrades and preferring removal keeps
the surface lean and secure over the product's life. This governs *how* dependencies are managed; it changes
no existing dependency.

## Alternatives Considered

- **Ad-hoc dependency adoption** — rejected: accretes lock-in and bloat (contra §9, §4.11).
- **Auto-upgrading everything** — rejected: risks breakage; upgrades are deliberate/governed (AD-5).
- **Never removing dependencies** — rejected: the surface rots; removal is preferred and governed (AD-6).

## Trade-offs

- **Governance overhead vs. long-term health:** requiring a lifecycle plan and review adds friction to
  adoption, but that friction is the point — it prevents un-exitable lock-in. Accepted.
- **Isolation seams vs. directness:** wrapping dependencies is a hair more indirect but makes them
  replaceable. Accepted (§4.14).

## Risks

- **Un-exitable lock-in.** *Mitigation:* AD-2 exit-strategy requirement + AD-4 isolation.
- **Security/accessibility regressions from a dependency.** *Mitigation:* AD-3 evaluation + AD-5 governed
  upgrades.
- **Bundle bloat.** *Mitigation:* performance-cost criterion (AD-3) + budgets ([04.8](04.8_Performance_Architecture.md)).

## Future Extension Points

- Automated dependency-health/security scanning and bundle-budget checks operationalize AD-3/AD-5 (tooling is
  Engineering's, out of scope here).
- A dependency ADR template standardizes the lifecycle-plan record ([05.6](05.6_Architecture_Decision_Record_Index.md)).
