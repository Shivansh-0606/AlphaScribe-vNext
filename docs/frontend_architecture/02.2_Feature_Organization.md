## Purpose

Define how the frontend is organized into **features** (bounded contexts), what constitutes a **shared
module**, how features **communicate**, the permitted **dependency direction** between them, and the
**scalability strategy** by which the system grows without accreting coupling.

## Scope

**In scope:** feature-based organization, shared modules, cross-feature communication, dependency
direction, scalability strategy. **Out of scope:** implementation; inventing features (scope is frozen);
routing/layout detail (02.3/02.4).

## Dependencies

## Architectural Decisions

### AD-1 — Features are the frozen IA domains (not invented)
Each feature is a **bounded context** corresponding to a frozen [IA domain](../design/03_Information_Architecture.md):

| Feature (bounded context) | Frozen IA domain | Notes |
|---------------------------|------------------|-------|
| `account-setup` | Account & AI Setup | session/identity + AI access (BYOK/Managed); precondition for all others |
| `workspace-home` | Workspace Home | entry + company search + recent research |
| `company-research` | Company Research | the core domain (overview, business summary, metrics, statements, filings, AI insights) |
| `comparison` | Comparison | **derived** — depends on company-research subjects (see AD-4) |
| `learning` | Learning | overlays company/filings with learner-level explanation |
| `research-library` | Research Library | sessions, reports, saved exports, history; Resume Session |

**No feature introduces capability beyond the frozen baseline.** (The M2 scope CRs — Portfolio/News/
Timeline — remain gated and are **not** features until approved.)

### AD-2 — Each feature exposes a small, stable public surface
A feature communicates only through its **public interface**; internals are private (§4.12). This is the
seam that keeps features independently evolvable and the system decoupled (§4.14).

### AD-3 — Shared modules hold cross-cutting, feature-agnostic concerns
Shared modules are depended on by features but depend on no feature:
- the **design-system component layer** (wrapped primitives + foundation/AI/research components),
- the **foundation/shared** layer (token consumption, shared types, utilities, accessibility harness,
  observability, error/fail-fast, motion vocabulary),
- the **integration/API-contract client** (typed + validated).

Cross-cutting product concepts that are genuinely shared across features (e.g. a **company** subject, a
**source reference**, a **research session**) are modeled in shared modules as stable contracts, since the
frozen [IA relationships](../design/03_Information_Architecture.md#information-relationships) make them
shared entities — not owned by any single feature.

### AD-4 — Dependency direction between features is controlled and acyclic
Features **do not depend on each other's internals**. Where the frozen IA defines a real relationship, it
is expressed through **shared contracts or routing**, never deep imports, and the graph stays **acyclic**:

- `account-setup` is a **precondition** (others assume an authenticated session + AI access) but is not
  imported by them — the dependency is enforced at routing/shell, not by code coupling.
- `comparison` is a **derived** domain: it references company subjects that originate in `company-research`
  (frozen IA: "a comparison always references companies that already exist as research subjects"). This
  reference is via the **shared `company` contract**, not a direct import of `company-research` internals.
- `learning` overlays `company-research`/filings via the **shared company/source contracts**, not internals.
- `research-library` **receives** output (sessions/reports) from `company-research` and `comparison` via
  shared contracts; it does not reach into their internals.

**Rule:** if feature A needs something from feature B, it goes through a **shared contract**, the **routing
layer**, or B's **public surface** — never B's internals; and the result must not create a cycle.

### AD-5 — Cross-feature communication patterns
Permitted mechanisms, in order of preference:
1. **Shared contracts / shared modules** (a stable, feature-agnostic model both depend on).
2. **Routing / navigation** (moving between features carries context via URL + persisted state, honoring
   frozen Navigation and never-lose-work — §6.3).
3. **A feature's public surface** (explicitly exposed capability), used sparingly and acyclically.
Direct imports of another feature's internals and hidden global coupling are prohibited (§4.10, §4.12).

## Scalability Strategy

- **Add a feature = add a bounded module** behind a public surface; the core and other features are
  untouched (§4.14). Growth is additive, not invasive.
- **Promote to shared** only when a cross-feature need is *proven* (avoid premature centralization, §4.11).
- **Progressive decoupling:** each milestone should leave feature seams stronger and cross-feature
  coupling lower, never higher (§4.14) — a review criterion.
- **Roadmap alignment:** later releases (e.g. Watchlists, and — if their CRs are approved — News/
  Portfolio) enter as new feature modules, keeping the MVP features stable.

## Design Rationale

Deriving features from the frozen IA binds the architecture to approved scope and makes it self-describing
(anyone who knows the product knows the module map). Bounded contexts with stable surfaces are the
mechanism by which a large, long-lived frontend stays changeable (§4.5, §4.12, §4.14). Routing shared
contracts (not imports) for cross-feature relationships prevents the coupling web that kills scalability.

## Alternatives Considered

- **Features importing each other directly** — rejected: creates cycles and ripple effects (contra §4.14).
- **A single "research" mega-feature** — rejected: low cohesion, poor ownership, doesn't scale; the IA
  already delineates distinct domains.
- **Global shared state as the cross-feature channel** — rejected: hidden coupling, unpredictable data
  flow (contra §4.10); shared *contracts* + explicit state ownership are used instead.

## Trade-offs

- **Shared contracts vs. directness:** routing a relationship through a shared contract is more ceremony
  than a direct import, but it keeps features independently evolvable. Accepted.
- **Bounded contexts vs. some duplication:** a little duplicated feature-local logic is preferred over
  premature shared coupling; shared-ness is earned (§4.11).

## Risks

- **Hidden cross-feature coupling** via shared mutable state or convenience imports. *Mitigation:*
  dependency rules + enforcement ([02.7](02.7_Module_Dependency_Rules.md)); explicit state ownership.
- **"Shared" becoming a dumping ground.** *Mitigation:* promotion requires a proven, repeated need and
  review; shared modules keep small, deliberate surfaces.
- **`comparison`/`learning` derived-dependency drift** into deep coupling. *Mitigation:* enforce the
  shared-`company`-contract rule (AD-4); acyclic graph verified in review.

## Future Extension Points

- New IA domains → new feature modules (additive).
- A feature may later be extracted to its own package (monorepo) via its public surface (§4.14).
- Shared contracts (company, source, session) are the stable extension points other features build on.
