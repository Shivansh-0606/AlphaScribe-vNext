## Purpose

Define the **principles that govern how data moves** through the frontend: its single, predictable
direction; the single-source-of-truth rule; how derived data is handled; and how data crosses feature and
layer boundaries — so the whole system's data behavior is anticipable and free of duplication.

## Scope

**In scope:** direction of data flow, single source of truth, derived data, cross-boundary data movement,
predictability rules. **Out of scope:** per-category detail ([03.1](03.1_State_Management_Strategy.md)–[03.9](03.9_Validation_Strategy.md)),
implementation.

## Architectural Decisions

### AD-1 — Data flows down, events flow up (unidirectional)
Data moves in **one direction**: **down** from its owner (Application layer state) into presentation as
props/bindings; user intent moves **up** as events to Application-layer use-cases, which change state, which
re-renders the view ([02.6 AD-4](02.6_UI_Layer_Architecture.md); §4.10). Presentational components never
mutate shared state directly and never reach sideways into other components' or features' state.

### AD-2 — Single source of truth per datum (the anti-duplication law)
Each datum has **exactly one authoritative home** ([03 AD-1](03_Data_and_State_Architecture.md)):
- server data → the **Query cache** (a copy of server truth, not a second authority),
- UI/ephemeral → the owning **Zustand** store,
- form input → **RHF**,
- location → the **URL**,
- derived values → **computed**, never stored.
No datum is copied across these homes. If two parts of the UI need the same datum, they **both read from its
single owner**, not from separate copies (the "prevent duplicated state" requirement).

### AD-3 — Derived state is computed, never stored
Any value that can be computed from existing state (a formatted figure, a filtered/sorted list, a
comparison delta, an aggregate) is **derived at read time** (via selectors/memoized computation), not stored
as its own state (§4.10). Storing derived values creates a second source of truth that drifts — prohibited.

### AD-4 — Cross-feature and cross-layer data movement is explicit and contract-bound
- **Across features:** data moves only through **shared contracts, the routing layer, or a feature's public
  surface** — never deep imports or hidden global coupling ([02.2](02.2_Feature_Organization.md), [02.7](02.7_Module_Dependency_Rules.md)).
- **Across layers:** data crosses only the sanctioned seams (Integration → Application → UI), inward-
  dependency-respecting ([02 AD-1](02_Application_Architecture.md)); the UI never fetches, the integration
  layer never renders.
Every crossing is explicit and typed (§4.9, §4.10, §4.12).

### AD-5 — Predictability is a first-class property
The same action always produces the same data flow and result ([Constitution §3 predictability, §4.10]).
Effects are visible and traceable; there is no hidden mutation, no implicit global side channel, and no
"magic" data appearing without a traceable owner (§4.10 explicitness over magic).

## Design Rationale

Unidirectional flow with a single source of truth per datum is the foundation of a predictable, debuggable,
scalable frontend — it eliminates the duplicated-state drift that is the most common cause of subtle UI
bugs, and it makes any datum's origin and update path traceable by reading. Computing derived state keeps the
truth in one place. Contract-bound cross-boundary movement keeps features decoupled and the layered
architecture intact.

## Alternatives Considered

- **Two-way binding / bidirectional data flow** — rejected: obscures the source of change and invites
  update loops (contra §4.10).
- **Duplicating server data into a client store for convenience** — rejected: the central anti-pattern this
  architecture exists to prevent (contra §4.3, AD-2).
- **Memoizing derived values into stored state** — rejected: creates drift; derived stays computed (AD-3).

## Trade-offs

- **Unidirectional discipline vs. quick local hacks:** flowing everything through owners/use-cases is more
  deliberate than a direct mutation, but it is what makes the system predictable at scale. Accepted.
- **Recomputing derived values vs. storing them:** recomputation costs a little CPU but guarantees
  correctness; memoization (compute-cached, not state) mitigates the cost without creating a second truth.

## Risks

- **Duplication creep** (copies of a datum appearing). *Mitigation:* AD-2 single-owner rule +
  [02.7](02.7_Module_Dependency_Rules.md) enforcement + review.
- **Hidden side channels** (global mutable coupling). *Mitigation:* §4.10 explicitness; prohibited by
  dependency rules.
- **Stored derived values.** *Mitigation:* AD-3; review flags any stored computable value.

## Future Extension Points

- New state categories (should a genuinely new one ever be justified) enter this taxonomy with a defined
  single owner — via governance, not ad hoc.
- Real-time data flows extend the down-flow model (server push → cache → UI) without changing direction.
