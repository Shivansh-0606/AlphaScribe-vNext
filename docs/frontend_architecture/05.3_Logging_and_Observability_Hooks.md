## Purpose

Define the **integration points** at which logging, metrics, tracing, and user-experience telemetry attach to
the frontend — the **architecture of observability**, per Constitution §4.15 (Observability by Design). It
defines **where hooks live and what they capture**, not tools, vendors, or implementation (deliberately
deferred).

## Scope

**In scope:** the observability integration points (logs, metrics, tracing, UX telemetry, diagnostics), what
each captures, and the privacy constraints on them. **Out of scope:** specific tools/vendors, OpenTelemetry
or any implementation, dashboards, and CI/CD or backend operational monitoring (excluded).

## Architectural Principles / Decisions

### AD-1 — Observability is designed-in as integration points, tool-agnostic
Per §4.15, observability is an architectural property realized as **hooks/integration points** in the
architecture, not instrumentation bolted on later. This document fixes **where** those points are and **what
signal** they carry; the **tooling/vendor is a later, governed decision** (§4.15 defers it).

### AD-2 — The four observability signal types and their hook points
| Signal | Captures | Hook point (from the architecture) |
|--------|----------|------------------------------------|
| **Logs** | Meaningful events at boundaries (navigation, use-case start/finish, boundary failures) | Application/integration boundaries ([02.6](02.6_UI_Layer_Architecture.md), [03.3](03.3_API_Layer_Architecture.md)) |
| **Metrics** | Health/performance counters (error rates, request timings, budget adherence) | Integration layer + performance seam ([04.8](04.8_Performance_Architecture.md)) |
| **Tracing** | Following a single flow/journey across boundaries (request → server → cache → UI) | Across the layered path ([02](02_Application_Architecture.md), [03.10](03.10_Data_Flow_Principles.md)) |
| **UX telemetry** | Perceived performance, journey completion, and **trust-critical path health** (AI grounding, never-lose-work) | UI + AI streaming ([03.13](03.13_AI_Streaming_Lifecycle_Architecture.md)), journeys (J-01–J-06) |

### AD-3 — Diagnostics are part of the failure path (reinforcing Fail Fast)
Every **unexpected failure** ([03.11](03.11_Error_Boundary_and_Recovery.md), §4.13) emits a **diagnostic** at
its containing boundary — so a fast failure is also a *legible* one. Notable expected failures on
trust-critical paths (e.g. repeated Partial Failure, unsourced-claim guards, lost-work guards) are also
observable. This is the observability side of Fail Fast.

### AD-4 — Trust-critical paths are first-class observability targets
Because the product is trust-first, the observability points prioritize the **trust-critical paths**: AI
grounding/traceability integrity, never-lose-work, and validation-boundary rejections — so a silent failure
in these is *impossible to miss* in production (§4.15, §4.13).

### AD-5 — Privacy is a hard constraint on all telemetry
Observability **must never leak sensitive research content, personal data, credentials, or user-provided AI
keys** (frozen privacy rules). Telemetry captures **events, timings, and health signals — not sensitive
payloads**; any potentially-identifying data is excluded or handled per the privacy policy. This constraint
governs every hook (AD-2) unconditionally.

### AD-6 — Observability is consumed, not the source of truth
Observability **reflects** system behavior; it never becomes application state or a second source of truth
([03.10](03.10_Data_Flow_Principles.md)). Hooks are side-channels for insight, decoupled from the data flow.

## Design Rationale

For a trust-first product, a *silent* failure in grounding or work-preservation is categorically
unacceptable — so observability must be architectural and must prioritize exactly those paths. Defining
tool-agnostic integration points (not instrumentation) keeps this implementation-agnostic and future-proof
against vendor choice, while ensuring the hooks exist where they matter. The privacy constraint keeps
observability consistent with the product's trust and privacy posture.

## Alternatives Considered

- **Bolt-on observability after launch** — rejected: gaps exactly where they hurt; §4.15 requires designed-in.
- **Choosing a specific tool/vendor now** — rejected: deferred by §4.15; the architecture fixes points, not
  tools.
- **Verbose logging of payloads** — rejected: privacy risk; telemetry carries events/health, not sensitive
  content (AD-5).

## Trade-offs

- **Instrumentation overhead vs. production insight:** hooks add a little overhead but make production
  legible and regressions catchable — essential for a trust-first product. Accepted.
- **Privacy-limited telemetry vs. debugging richness:** excluding sensitive payloads reduces some debugging
  detail but is non-negotiable (AD-5). Accepted.

## Risks

- **Silent failures on trust-critical paths.** *Mitigation:* AD-3/AD-4 diagnostics + prioritized hooks.
- **Privacy leakage via telemetry.** *Mitigation:* AD-5 hard constraint; review of what each hook captures.
- **Observability coupling into app state.** *Mitigation:* AD-6 side-channel rule.

## Future Extension Points

- Tooling/vendor selection and dashboards are a governed future decision (Engineering + CTO).
- Backend/end-to-end tracing correlation extends AD-2 when the backend contract/observability aligns.
- Alerting/SLOs build on the metrics hooks (ops concern, out of scope here).
