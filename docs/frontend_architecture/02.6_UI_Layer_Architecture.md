## Purpose

Define the **UI layer**: its internal sub-layers, the split of rendering responsibilities (server vs.
client), where interaction lives, how presentation flows from data to view, and the separation of concerns
that keeps presentation, behavior, and data distinct. This is architecture; it renders no actual UI.

## Scope

**In scope:** UI sub-layers, rendering responsibilities, interaction boundaries, presentation flow,
separation of concerns. **Out of scope:** implementation, page/screen design, state/data implementation
(architected here, built later).

## Architectural Decisions

### AD-1 — The UI layer is internally sub-layered by concern
Within the Presentation/UI layer ([02 AD-1](02_Application_Architecture.md)), responsibilities are
separated (§4.3):

```
Rendering sub-layer        decides & performs server vs. client rendering (§7); owns the server/client seam
Presentation sub-layer     pure presentational components (design system) — render from props (02.5 AD-5)
State-binding sub-layer     connects presentation to client state (Zustand) — read/subscribe/dispatch (arch only)
Data-binding sub-layer      connects presentation to server state (TanStack Query) + forms (RHF+Zod) (arch only)
Interaction sub-layer       handles user input/events, delegates to application use-cases (02 interaction model)
```

Each sub-layer has one concern; presentation stays pure, binding/interaction stay thin, behavior lives in
the application layer.

### AD-2 — Rendering responsibilities (server vs. client)
Per Constitution §7:
- **Server rendering (default)** owns content-led, read-heavy, low-interactivity presentation (e.g.
  reading statements, filings, reports) — minimal client cost, better perceived performance, SEO for
  public surfaces.
- **Client rendering (islands)** owns genuine interactivity and live experience — the AI companion,
  streaming output, forms, rich interaction and motion.
- **The seam is explicit and minimal:** interactivity is the reason to become a client island; islands are
  scoped as tightly as the interaction requires, to bound hydration cost (§4.7).

### AD-3 — Interaction boundaries
- Interactivity is confined to **client islands**; the surrounding content can remain server-rendered.
- **Events flow one way**: an interaction delegates to an **application-layer use-case**, which owns
  behavior and decides state changes; the UI does not embed business logic (§4.10, [02.5](02.5_Component_Architecture.md)).
- **Motion** is applied at this boundary via the frozen [Motion
  spec](../experience_design/engineering_handoff/05_Motion_Specifications.md) — reduced-motion honored
  losslessly (§4.6).

### AD-4 — Presentation flow is unidirectional
Data flows **down** (into presentational components as props), events flow **up** (to use-cases); the view
is a function of state (§4.10 explicitness, predictable data flow). No component mutates shared state
directly or reaches sideways into another feature.

### AD-5 — State rendering follows the frozen States catalogue + Fail Fast
Every surface renders the applicable frozen [States](../design/13_States.md) as **first-class**:
- **Expected states** (Loading, Skeleton, Empty, No Results, Offline, Permission Denied, Auth Required,
  Error, Partial Failure, Success, Timeout, AI Thinking/Streaming) are handled **gracefully and
  accessibly** — never a dead end, never lost work (frozen States rules).
- **Unexpected conditions** (invalid data, contract violations) **fail fast** (§4.13): surfaced
  immediately via an error boundary with diagnostics, work preserved, never silently rendered as if valid.
- **AI presentation** keeps AI content visibly distinct from source, with citations reachable — a UI-layer
  obligation inherited from the frozen trust rules.

### AD-6 — Separation of concerns (the UI contract)
- **Presentation** knows how to *display*, not what data means or where it comes from.
- **Behavior** (use-cases) lives in the application layer, invoked via the interaction sub-layer.
- **Data** (server/client state) is owned by the application/integration layers and *bound* into
  presentation, never fetched inside a presentational component.
- **Accessibility** (semantics, focus, announcements) and **motion** are structural properties of the UI
  layer, not per-screen afterthoughts (§4.6; frozen Accessibility/Motion).

## Design Rationale

Sub-layering the UI by concern is what makes presentation reusable and testable, keeps behavior and data
out of the view, and makes the server/client split a deliberate performance decision rather than an
accident (§4.3, §4.7, §7). Making frozen States first-class and pairing graceful expected-state handling
with fail-fast on the unexpected operationalizes the product's trust and never-lose-work promises at the
exact layer the user experiences them (§4.13).

## Alternatives Considered

- **Fat components** (fetching + state + rendering together) — rejected: unpredictable data flow, poor
  testability/reuse (contra §4.3, §4.10).
- **Blanket client rendering** — rejected: hydration cost, weaker perceived performance/SEO (contra §7,
  §4.7).
- **Treating error/empty states as edge cases** — rejected: they are the trust surface and are frozen
  first-class States (§4.13).

## Trade-offs

- **Sub-layer separation vs. verbosity:** more seams (binding/interaction sub-layers) add indirection but
  buy testability and reuse. Accepted.
- **Island scoping vs. simplicity:** finely scoped client islands optimize hydration but require care at
  the server/client seam; justified by performance (§4.7).

## Risks

- **Server/client seam misplacement** (logic on the wrong side; hydration mismatch). *Mitigation:*
  explicit per-surface rendering decisions (AD-2) against performance budgets; review.
- **Business logic leaking into presentation.** *Mitigation:* SoC contract (AD-6); use-cases own behavior.
- **Incomplete state coverage** (missing empty/error/partial). *Mitigation:* frozen States are a
  Definition-of-Done + Design QA item.

## Future Extension Points

- New interaction modalities attach at the interaction sub-layer without touching presentation.
- Streaming/real-time surfaces extend the client-island model (§7) without restructuring server content.
- Observability hooks (§4.15) attach at the interaction/data-binding sub-layers in a later milestone.
