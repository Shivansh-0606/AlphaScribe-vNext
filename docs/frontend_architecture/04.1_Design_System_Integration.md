## Purpose

Define how the **frozen design system** — the Experience Design component families and the **shadcn/ui**
primitive layer — is **architecturally integrated** into the application: the integration boundary, the
wrapping model, the layering, and the ownership split. It restates and applies (does not change) the
component decisions of [M2 02.5](02.5_Component_Architecture.md) and the frozen
[Engineering Handoff](../experience_design/engineering_handoff/12_Component_Mapping.md).

## Scope

**In scope:** the design-system integration boundary, the primitive-wrapping model, component layering
integration, and the design/architecture/engineering ownership split for the component system. **Out of
scope:** implementing components, redesigning them, modifying tokens/visuals (frozen; §6.5), and the token
pipeline itself ([04.2](04.2_Design_Token_Consumption_Strategy.md)).

## Architectural Decisions

### AD-1 — The design system is integrated behind a wrapping boundary (wrap, don't consume raw)
Every **shadcn/ui primitive is wrapped** by an AlphaScribe component that binds it to tokens
([04.2](04.2_Design_Token_Consumption_Strategy.md)), states ([03.14](03.14_Data_Ownership_Matrix.md)), and
accessibility ([04.5](04.5_Accessibility_Architecture.md)). **Features and screens never import shadcn
primitives directly** ([02.5 AD-3](02.5_Component_Architecture.md), [02.7](02.7_Module_Dependency_Rules.md)).
The wrapper boundary is the integration seam.

### AD-2 — The frozen component layering is the integration structure
Integration follows the frozen layering ([Component families](../experience_design/Components/00_Component_System.md);
[02.5 AD-1](02.5_Component_Architecture.md)): **primitives → foundation → AI → research → feature → screen**.
Each layer composes only lower layers (composition over inheritance, §4.4). The design system supplies
layers 1–4; the app composes 5–6. No new primitives are introduced by integration.

### AD-3 — The integration boundary isolates the primitive library (progressive decoupling)
Because primitives are wrapped, the primitive library is **isolated behind a stable seam** (§4.12, §4.14):
a change to a primitive, or a future replacement of the primitive library, is a **localized change to
wrappers**, not a rewrite across the app. This directly realizes the dependency exit-strategy rule
(Constitution §9) and insulates the product from primitive/library churn.

### AD-4 — Ownership split (§6.5) is enforced at integration
| Concern | Owner |
|---------|-------|
| Component visual/interaction spec + tokens | **Design** (frozen; CR to change) |
| Wrapping boundary, layering, public interfaces, composition rules | **Frontend Architecture** |
| Wrapper/component implementation, optimization, tests | **Frontend Engineering** |
Integration never alters a component's design; it binds and layers it.

### AD-5 — Stable public interfaces mirror the frozen variant vocabulary
Each wrapped component exposes a public interface whose **variant/size/state vocabulary matches the frozen
[Component Mapping](../experience_design/engineering_handoff/12_Component_Mapping.md) 1:1** (§4.12). A visual
variant that is not in the design does not exist in code; a design variant is never silently dropped.

### AD-6 — The design system is a versioned dependency
The design system (its component library + tokens) is treated as a **governed dependency** of the app
(Constitution §9): its version is tracked, upgrades are deliberate, and changes flow through the design CR
process ([Design System Governance](../experience_design/engineering_handoff/13_Design_System_Governance.md)).

## Design Rationale

Wrapping the primitive library and integrating along the frozen layering concentrates the token/a11y/state
binding in one place per component, guarantees fidelity to the frozen specs, and makes the whole component
system resilient to primitive/library change — the classic risk in a shadcn-based system. Enforcing the
ownership split keeps architecture from becoming a redesign vector. Together these deliver the design system
consistently while keeping the app free to evolve.

## Alternatives Considered

- **Consuming shadcn primitives directly in screens** — rejected: scatters token/a11y binding, couples every
  screen to the primitive library, turns a primitive swap into a rewrite (contra §4.14, frozen handoff).
- **Forking/copying the design system into the app** — rejected: forks drift from the frozen source; the
  design system is consumed as a governed dependency, not copied.
- **A bespoke component library instead of shadcn** — rejected: the stack (shadcn) and the frozen handoff
  are approved; a bespoke library is out of scope and a CR.

## Trade-offs

- **Wrapping overhead vs. insulation:** a thin wrapper per primitive is extra surface, but it buys
  token/a11y consistency and swap-ability. Accepted.
- **Strict layering vs. shortcut composition:** disallowing cross-layer shortcuts adds discipline but keeps
  the system predictable and changeable. Accepted.

## Risks

- **Raw-primitive usage** leaking into features/screens. *Mitigation:* dependency rules + lint + Design QA
  ([02.7](02.7_Module_Dependency_Rules.md), [04.5](04.5_Accessibility_Architecture.md)).
- **Wrapper drift** from the frozen spec (extra/missing variants). *Mitigation:* 1:1 with Component Mapping;
  QA.
- **Design-system version drift.** *Mitigation:* governed dependency (AD-6); versioning per the frozen
  Design System Governance.

## Future Extension Points

- A primitive-library change/replacement is absorbed at the wrapper boundary (§4.14).
- New design-system components (via design CR) integrate at their correct layer with a full spec.
- The wrapping boundary supports extracting the component layer into a shared package if team scale warrants.
