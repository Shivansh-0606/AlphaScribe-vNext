## Purpose

Define the **testing philosophy and architecture** for the frontend: what is tested, at which level, with
what priority — so correctness (especially of the product's **trust-critical paths**) is verifiable and
maintained. It defines a **strategy**, not test code, tooling, or CI pipelines (out of scope).

## Scope

**In scope:** the testing philosophy, test levels and their responsibilities, what to test where, priority of
trust-critical paths, and how testing relates to accessibility and design QA. **Out of scope:** test
implementation/code, specific test runners, and CI/CD pipelines (excluded).

## Architectural Decisions

### AD-1 — A layered test strategy (a pragmatic pyramid)
Testing is organized in layers, each with a clear responsibility; the base is broad and fast, the top narrow
and high-value:
| Level | Verifies | Owner boundary it targets |
|-------|----------|---------------------------|
| **Unit** | Pure logic: validation schemas, formatters, use-case/behavior logic, derived-state computation | Application / foundation ([03.9](03.9_Validation_Strategy.md), [03.10](03.10_Data_Flow_Principles.md)) |
| **Component** | A component's behavior, states, and **accessibility** (roles/names/keyboard) | Component layer ([02.5](02.5_Component_Architecture.md), [04.5](04.5_Accessibility_Architecture.md)) |
| **Integration** | A feature's flows across its layers (UI ↔ application ↔ integration, with the boundary mocked) | Feature module ([02.2](02.2_Feature_Organization.md)) |
| **End-to-end (journey)** | The approved user journeys **J-01…J-06** end to end | Whole app ([User Journeys](../design/02_User_Journeys.md)) |
| **Accessibility** | WCAG AA: automated (axe) + manual keyboard/SR | Cross-cutting ([04.5](04.5_Accessibility_Architecture.md)) |
| **Visual regression** | Fidelity to the approved design (once screen baselines exist) | Cross-cutting (Design QA baselines) |

### AD-2 — Trust-critical paths are tested first and most
The product's promises define the highest-priority tests: **AI grounding/traceability** (every claim
sourced; AI distinct from source — [03.13](03.13_AI_Streaming_Lifecycle_Architecture.md)), **never-lose-work**
(work preserved across error/nav/timeout; Resume Session — [03.11](03.11_Error_Boundary_and_Recovery.md)),
**validation at trust boundaries** ([03.9](03.9_Validation_Strategy.md)), and **state ownership / no
duplication** ([03.14](03.14_Data_Ownership_Matrix.md)). These paths get the deepest coverage.

### AD-3 — Test at the right boundary (leverage the architecture)
Because the architecture separates concerns and defines stable public interfaces (§4.3, §4.12), tests target
**public surfaces and boundaries**, not internals — pure logic at the unit level, behavior at the component/
integration level, journeys at E2E. This keeps tests resilient to refactoring (they assert contracts, not
implementation).

### AD-4 — Frozen States and edge cases are first-class test targets
Every surface's **frozen [States](../design/13_States.md)** (loading, empty, no-results, error, partial
failure, offline, timeout, permission-denied, success) and the edge cases named in the Experience
[Component Specs](../experience_design/engineering_handoff/02_Component_Specifications.md) are explicit test
cases — not just the happy path. Fail-fast behavior ([04.13]/§4.13) is tested to *fail*, not silently pass.

### AD-5 — Accessibility testing is part of the definition of done
A component/screen is not "tested" until its accessibility is verified (automated axe **and** the manual
keyboard/SR pass from [04.5](04.5_Accessibility_Architecture.md)/[Design QA](../experience_design/engineering_handoff/10_Design_QA_Process.md)).
Accessibility tests are a merge gate, not optional.

### AD-6 — Design QA complements engineering testing
Two verification tracks (from the Experience handoff): **engineering tests** (correctness/behavior) and
**Design QA** (visual fidelity, token compliance, responsive, motion, cross-screen). Both are required; this
document owns the former and defers the latter to the frozen [Design QA Process](../experience_design/engineering_handoff/10_Design_QA_Process.md).

## Design Rationale

A layered strategy that leverages the architecture's boundaries gives fast, resilient tests where they are
cheap and high-value tests where they matter, while front-loading the trust-critical paths that define the
product. Making frozen States and accessibility first-class test targets ensures the trust and inclusivity
guarantees are verified, not assumed. Keeping this a *strategy* (not code/pipelines) respects the milestone
scope while giving Engineering an unambiguous testing frame.

## Alternatives Considered

- **E2E-heavy ("ice-cream cone") testing** — rejected: slow, brittle, expensive; the pyramid favors fast unit/
  component tests with focused E2E on journeys.
- **Happy-path-only testing** — rejected: the frozen States and edge cases are the trust/robustness surface
  (§4.13, AD-4).
- **Deferring accessibility tests to QA only** — rejected: a11y is a merge gate and an Immutable Law (§17;
  [04.5](04.5_Accessibility_Architecture.md)).

## Trade-offs

- **Test coverage vs. speed:** deep coverage of trust-critical paths costs time but protects the product's
  core promises; broad shallow coverage elsewhere is kept fast. Accepted.
- **Boundary testing vs. internal coverage:** testing public surfaces (not internals) yields resilient tests
  at the cost of some internal-branch visibility; the trade favors maintainability (§4.12).

## Risks

- **Under-tested trust-critical paths.** *Mitigation:* AD-2 priority + review checklist ([05.9](05.9_Architecture_Review_Checklist.md)).
- **Brittle internal-coupled tests.** *Mitigation:* boundary-targeted testing (AD-3).
- **Accessibility regressions.** *Mitigation:* a11y as a gate (AD-5; [04.5](04.5_Accessibility_Architecture.md)).

## Future Extension Points

- Concrete runners/frameworks and CI wiring are selected by Engineering within this strategy (out of scope
  here).
- Contract testing against the backend API can extend integration tests when the contract is formalized
  ([03.3](03.3_API_Layer_Architecture.md)).
- Visual-regression baselines attach when Experience M2 Phases 3–5 (screens/library) land.
