# `components/foundation` — AlphaScribe wrappers (Families 01–07 + Overlays + SearchField)

AlphaScribe wrappers of shadcn primitives (Button, Input, …). Each wrapper binds design tokens, interaction states, and accessibility semantics — and never strips primitive semantics (04.5 AD-3). Presentational only; no feature logic (02.5).

Every component here wraps the raw generated primitive in `components/ui/` — never import from `components/ui` outside this directory (02.7 AD-2).

## Built so far

### Family 01 — Buttons ([spec](../../docs/experience_design/Components/01_Buttons.md))

**`Button`** — Trigger a single, discrete action.

- **Variants:** `primary` (solid ink-navy; add `hero` for the brand gradient on the one hero action per context) · `secondary` (surface fill, hairline border) · `quiet` (no fill) · `destructive` (solid red) — exactly these four, per the frozen spec.
- **Sizes:** `sm` (28px) · `md` (36px, default) · `lg` (44px).
- **Props:** `variant`, `size`, `hero`, `loading` (keeps width, sets `aria-busy`, spinner replaces content in place, non-activatable), `asChild` (Radix `Slot` composition), plus all native `<button>` props.
- **Accessibility:** native `<button>`; label is always the accessible name; loading/disabled communicate via more than color (aria-busy/aria-disabled + reduced opacity); focus ring inherited from the global `:focus-visible` rule (not re-declared per-component, to avoid divergence).
- **Usage:** exactly one `primary` per view/region (§7.1) — never two competing primaries, never `hero` on more than one button.

**`IconButton`** — A Button whose label is visually an icon but semantically still a name.

- **Variants:** `quiet` (default) · `secondary` · `primary` (rare) · `destructive`.
- **Sizes:** `sm` (28px) · `md` (36px, default) · `lg` (44px, touch-primary).
- **Props:** `label` (**mandatory** — becomes `aria-label`; there is no way to render this component without an accessible name), `icon` (a Phosphor glyph, rendered `aria-hidden`), `loading`, `pressed` (toggle → `aria-pressed`).
- **Accessibility:** the glyph never carries the name; `label` always does. Pair with a `Tooltip` (Family 06) for sighted pointer users — never as the _only_ name source.

### Typography (token realization, not a numbered Family)

Realizes the frozen semantic type roles (`03_Typography_System.md` §Semantic Type Roles) as reusable, strongly-typed components. Not a Component Family — typography is a foundation/token concern — but a first-class primitive per the M2 objectives.

**`Heading`** — `level` (`h1`/`h2`/`h3`, defaults to matching element) + optional `as` when the visual level must differ from the semantic element. Caller is responsible for sequential order (h1→h2→h3, no skips).

**`Text`** — `variant`: `body` · `body-strong` · `small` · `caption` · `label` (the uppercase mono micro-label — distinct from the _form_ `Label` primitive, Phase 2) · `figure` (tabular mono for financial values) · `code`. Optional `as` override.

**`Link`** — Internal paths (`/…`) render Next's `Link`; anything else renders `target="_blank" rel="noopener noreferrer"` with an accessible "(opens in new tab)" suffix. Styled per the frozen link/brand color + underline (never color alone, §17).

### Family 02 — Text Inputs ([spec](../../docs/experience_design/Components/02_Text_Inputs.md)) + Family 03 — Selection Controls ([spec](../../docs/experience_design/Components/03_Selection_Controls.md))

**`FormField`** — label + control + reserved-height help/error region. Wraps a single child control (`Input`, `Textarea`, a `SelectTrigger`, …) via `cloneElement`, injecting `id`/`aria-describedby`/`aria-invalid` automatically — the caller never wires these by hand. Error takes priority over help text (only one ever renders; `aria-describedby` references only the id that actually exists in the DOM).

**`ValidationMessage`** / **`HelperText`** — standalone error/help text primitives (`role="alert"` + icon / muted caption respectively). Used inside `FormField`, but also standalone for group-level errors (e.g. a Checkbox/RadioGroup "select at least one").

**`Input`** — `type`: `text`/`email`/`password`/`tel`/`url`/`number`. `password` gets a **mandatory** reveal toggle (`aria-pressed`, never announces the value). `leadingIcon`/`trailingAddon` slots. Sizes `sm`/`md`/`lg`.

**`Textarea`** — auto-grow via the native CSS `field-sizing: content` (no JS resize handler). `showCounter` + `maxLength` render a "used/max" counter that warns near the limit — never silently truncates.

**`Checkbox`** — `checked` accepts Radix's `boolean | "indeterminate"` directly (`aria-checked="mixed"`) — no ref/DOM hack needed. `label` is required; label+box are one clickable unit. Composes the raw `radix-ui` Checkbox primitive directly rather than the generated `components/ui/checkbox.tsx` — that generated file only styles `data-[state=checked]` (no `indeterminate` rule) and hardcodes a checkmark glyph for both states; found via real-browser computed-style verification (indeterminate rendered with no fill, same as unchecked) and fixed by adding the missing fill classes + a distinct `Minus` glyph for indeterminate, per the spec's "distinct glyphs (✓ vs –)" requirement.

**`RadioGroup`** / **`RadioGroupItem`** — native `<fieldset>`/`<legend>` group; Radix's roving-tabindex model (Tab enters/exits the group, arrows move **and select** within it — confirmed via real-browser test, not assumed; see the pitfall note in `tests/e2e/component-fixtures.spec.ts`).

**`Switch`** — immediate-effect toggle. `showStateLabel` (on by default) renders the mandatory textual On/Off cue — the spec requires knob position **and** a state label, never color alone.

**`Select`** / **`SelectTrigger`**/etc. — native-backed Radix Select. Sub-components re-exported as generated (already correctly token-bound); only `SelectTrigger` is wrapped, to add the frozen `lg` size shadcn doesn't ship.

**`DropdownMenu`** and sub-components — re-exported as generated; already implements the frozen contract (destructive items via `variant="destructive"`, Esc returns focus to the trigger, first item focused on open).

**Not built yet:** `SearchField` — deferred to Phase 5 (Overlays), since it composes `Popover` per the Component Mapping.

### Family 05 — Content & Data Display ([spec](../../docs/experience_design/Components/05_Content_Data_Display.md))

**`Card`** / **`CardHeader`**/**`CardContent`**/**`CardFooter`**/**`CardTitle`**/**`CardDescription`**/**`CardAction`** — Direction C: flat at rest, elevation only on interaction. The generated primitive's own `rounded-xl`/`shadow-sm`/`py-6` are cancelled (`rounded-md`/`shadow-none`/`py-4`, the frozen radius + comfortable padding) the same way `Button.tsx` cancels shadcn's default fill; `Header`/`Content`/`Footer` default to `--space-4` padding instead of the generated `px-6` (pass `className="px-3"` for dense grids). `variant="interactive"`/`"selectable"` add hover lift / a selected ring cue, but grant no focusability themselves — compose the actual focusable element (a `Link`, a `RadioGroupItem`, …) via `asChild` (Radix Slot) so there's exactly one focusable control per card. Loading/Empty/Error are caller-composed content, not component props — Card is presentational only (compose `SkeletonGroup`/`Skeleton`, Family 07, for the loading case).

**`Table`** / **`TableBody`**/**`TableFooter`**/**`TableCaption`**/**`TableRow`** — re-exported as generated (native `<table>` semantics + the horizontal-scroll container shadcn already wraps it in, satisfying "scroll within the region, not the page"). **`TableHeader`** adds `sticky` (sticky header on scroll). **`TableHead`** adds `numeric` (right-aligned tabular mono) and `sortDirection`/`onSort` (sets `aria-sort`, renders an interactive trigger with a direction caret). **`TableCell`** adds `numeric` and `unavailable` (renders explicit "Not available" — or a custom string like "Not comparable" — instead of a silently blank cell, per the Partial Failure rule).

**`Chip`** — no shadcn primitive maps to this token (Component Mapping: "wrapped token"); built directly on native elements. `variant` drives semantics, not just visuals: `filter`/`choice` render a real `<button>` (toggle vs. single-select action — `filter` reflects `aria-pressed` + a non-color selected cue); `removable`/`static` render a non-interactive `<span>`. `onRemove` (any variant) renders a trailing ✕ via `IconButton`, itself its own focusable, labeled ("Remove {label}") control — never part of the chip's own click target.

**`Badge`** — meaning-bearing, never color alone (§17): `children` (the text label) is required. Wraps the generated `components/ui/badge.tsx` but replaces its variant vocabulary entirely: `neutral`/`bullish`/`bearish`/`warning`/`verified`/`count`, each with an explicit `bg-*` class cancelling the primitive's default fill (same mechanism as Button's `quiet` variant).

**`Avatar`** — the generated primitive already ships `AvatarImage`/`AvatarFallback`/`AvatarBadge`/`AvatarGroup`/`AvatarGroupCount`; this wrapper binds `name` as the **mandatory** accessible name (`role="img"` `aria-label`, never "avatar") and its initials source (first + last word), and maps the frozen `sm`/`md`/`lg` size vocabulary onto shadcn's `sm`/`default`/`lg`. `statusLabel` renders the status dot with its own `role="img"` textual name (e.g. "Online") — never a color-only cue.

### Generic layout primitives (M2 Phase 3 — not a numbered design Family)

Engineering conveniences over the frozen `--space-N` scale ([04_Spacing_System.md](../../docs/experience_design/04_Spacing_System.md)) and the [Grid System](../../docs/experience_design/05_Grid_System.md)'s 12/8/4 column model — no dedicated spec doc numbers these, unlike Families 01–09.

**`Flex`** — generic flexbox (`direction`, `gap`, `align`, `justify`, `wrap`, `as` for polymorphism). Exports `GAP_CLASS`/`SpaceStep`, the single mapping from a `--space-N` step to the Tailwind gap utility that realizes it (Tailwind's own scale already contains every one of those exact px values — no separate CSS custom properties exist for spacing, see the doc's Decision Rationale) — `Stack`, `Grid`, and `Spacer` import this rather than re-deriving it.

**`Stack`** — the vertical-rhythm shorthand for `Flex` (`direction="col"`); composition, not a separate implementation.

**`Grid`** — CSS grid over the 12/8/4 column system. `cols` accepts a fixed number or a `{ base, md, lg }` object matching the doc's mobile/tablet/desktop bands, realized via inline custom properties + Tailwind's arbitrary-value `grid-cols-[var(--x)]` syntax (the same pattern `tokens.css` documents for z-index) — a template-interpolated class name (`` `grid-cols-${n}` ``) would be invisible to Tailwind's static scanner.

**`Container`** — the page-edge margin + max-width wrapper (`--grid-max-content` ≈ 1280–1440px). `reading` swaps the max-width to `--reading-max` (72ch) for long-form research text.

**`Spacer`** — an explicit one-off rhythm gap on one axis (`size` + `axis`), `aria-hidden`. Prefer `gap` on `Flex`/`Stack`/`Grid` where possible (the spacing doc's own "prefer gap over margins" guidance) — this is for the rarer case of a single gap between elements not already in a gapped container.

**`Divider`** — re-exported as generated (`Separator as Divider`): already implements the frozen contract (horizontal/vertical, decorative by default) via Radix, same "pure re-export" precedent as `DropdownMenu`.

### Family 07 — Feedback & Status ([spec](../../docs/experience_design/Components/07_Feedback_Status.md))

**`Progress`** — composes the raw `radix-ui` Progress primitive directly rather than the generated `components/ui/progress.tsx` (the same reason `Checkbox.tsx` bypasses its generated primitive): the generated file bakes the determinate `translateX` math and a hardcoded `bg-primary` fill straight into its own JSX with no way to opt into an indeterminate sweep or a `tone`-selected fill. `value` omitted → indeterminate (a fixed-width segment runs a continuous `@keyframes progress-indeterminate` sweep, defined in `app/globals.css` since it isn't one of Tailwind's built-in `animate-*` utilities); `value` (0–100) → determinate, width set via inline style. `label` is **mandatory** (`aria-label`) — a progress bar is never the only signal for a wait, and indeterminate has no `aria-valuenow` for a screen reader to announce otherwise. `tone="brand"` is the sanctioned gradient fill for AI/primary flows; `tone="neutral"` (default) otherwise. **Not built:** a dedicated named-step "stage" tracker — Family 08's AI Thinking State owns staged AI progress UI; forking a duplicate stepper here would just be redone there.

**`Skeleton`** / **`SkeletonText`** / **`SkeletonGroup`** — the generated `components/ui/skeleton.tsx` is already token-bound (`bg-accent`, `rounded-md`) and its `animate-pulse` already honors the global reduced-motion override in `globals.css`; re-exported as the base shape primitive, always `aria-hidden` (placeholders are never read as real data). `SkeletonText` is a convenience for the common "N lines, last one shorter" shape. `SkeletonGroup` wraps a set of shapes in `role="status"` with one real, visually-hidden "Loading" announcement for the whole region — the spec's "single loading status, not per-shape" rule, the same centralize-the-a11y-wiring reasoning as `FormField`. **Not built:** dedicated `SkeletonTable`/`SkeletonCard`/`SkeletonChart` presets — those shapes are dimension-matched to their real content 1:1, so they're composed from `Skeleton` at the actual call site (a real `Table`/`Card`/chart consumer) rather than guessed here in the abstract.

**`Loader`** — no shadcn primitive maps to this token (Component Mapping: "wrapped · Motion"); built directly on the same `CircleNotch` spinner Button.tsx/IconButton.tsx already render for their own `loading` prop. Covers the spec's **Region**/**Full-view** variants only — **Inline** (in a button/field) is already those two components' existing inline spinner; this isn't a refactor of that. `role="status"` with a real, visible `label` (not just an aria-label) — busy semantics always pair with readable text per spec. `fullView` is the rare initial-boot-only case: fixed and centered over the viewport.

**`Banner`** — the **inline banner** variant of Notification (Component Mapping: "region banner / list", no shadcn primitive). Persistent region-level status (Offline, Partial Failure, a permission notice) — not a transient outcome (that's `sonner`, see Toast below). `tone` picks exactly one of four plain per-tone class strings (like `Button`'s `variant`), never a `data-[attr]:` CSS conditional layered on an unconditional class — deliberately avoiding the specificity-tie bug documented for `Chip` below, since only one tone's classes are ever in the DOM at once. `role="alert"` (assertive) for `warning`/`error`, `role="status"` (polite) for `info`/`success`, per the spec's "role=status/alert per severity" rule. **Not built:** the notification-list-item variant — it composes a `ListItem` primitive (Inventory) that doesn't exist yet; deferred until that primitive lands rather than forked here.

**Toast — documentation only, no wrapper component.** Per the Component Mapping, Toast maps directly to **`sonner`**, not a shadcn primitive — this is a project-wide convention (see the project's root `CLAUDE.md`), not a Family 07 gap. `sonner`'s `<Toaster />` is already mounted at the app root in `providers/AppProviders.tsx`, token-bound (`bg-surface`/`text-foreground`/`border-border` via `toastOptions.classNames`) and positioned `bottom-right`. Call `toast()`/`toast.success()`/`toast.error()` directly from `sonner` at the call site — do not wrap it in a `Toast` foundation component; there's no primitive here to bind tokens to beyond what's already configured on `<Toaster />`. Toasts are for transient **outcomes** only (never a blocking/critical error — use the Error state, or `Banner` above for a persistent condition).

### Family 06 — Overlays ([spec](../../docs/experience_design/Components/06_Overlays.md))

**`Tooltip`** — composes Root/Trigger/Content into one component (`content` + `children`, like `FormField` wires label/control/help). Overrides the generated primitive's inverted `bg-foreground`/no-shadow/`z-50` bubble with the frozen `--popover` surface + `--shadow-md` + `--z-overlay`. Uses `forceMount` on `Portal`/`Content` with `data-[state=closed]:opacity-0 pointer-events-none` doing the actual hide-at-rest — **required**, not stylistic: without it, opening via keyboard focus (never hover) reproducibly self-closed on the very next tick, 100% of the time. Root cause (traced via Radix's own source, confirmed against a full `next build && next start`, not dev-mode only): `TooltipContent` subscribes to a document-level `"tooltip.open"` event for cross-instance mutual exclusion, in a mount effect — on the synchronous focus path, that effect and the dispatch from opening race in the same commit, so Content catches its own just-fired open event and immediately closes itself. The delayed hover path (a real `setTimeout`) never raced this way. `forceMount` sidesteps the race by mounting Content once, up front, instead of exactly when it needs to become visible.

**`Popover`** — Root/Trigger/Anchor/Header/Title/Description re-exported as generated (already `bg-popover`/`shadow-md`/`border`-correct); only `PopoverContent` is wrapped, to swap the raw `z-50` for `--z-overlay`.

**`Dialog`** / **`Drawer`** — both compose the raw `radix-ui` Dialog primitive directly rather than their generated `components/ui/dialog.tsx`/`sheet.tsx` (the same reason `Checkbox`/`Progress` bypass theirs): the generated `Content` bakes its own unstyleable `Overlay` call into its JSX, with no way to pass a differently-tokened one in or to omit it for `Drawer`'s non-modal case. Off-token values replaced (04.2 AD-3): scrim `bg-black/50` → `bg-foreground opacity-scrim`; `Dialog`'s panel `rounded-lg`/`bg-background` → `rounded-md`/`bg-popover`; `Drawer`'s panel → `bg-surface` (the spec's distinct token for an edge-anchored surface) with no added radius (sharp edges, and the generated primitive already had none); layering/motion `z-50`/raw durations → `--z-modal`/`--z-drawer`/`--motion-duration-slow`. Neither has a `showCloseButton` shortcut that renders a raw, non-token-bound button — compose `DialogClose`/`DrawerClose` with the foundation `IconButton`/`Button` explicitly.
`Drawer`'s `modal` prop only toggles whether it renders its own scrim — pass the _same_ `modal={false}` to the `Drawer` root too (Radix's own prop). **Traced, not assumed**, what `modal` actually changes: `FocusScope`'s `loop: true` is hardcoded for Dialog-based content regardless of `modal`, so Tab always cycles within an open drawer's own focusable elements either way. What genuinely differs is `disableOutsidePointerEvents` — modal makes the rest of the page inert to pointer events entirely (confirmed: a real click on another button times out); non-modal leaves it fully interactive, matching the spec's "the user moves between content and companion freely." **Not built:** the AI companion's own streaming/thinking states — Family 08's `CopilotPanel` owns that, not forked here.

**`SearchField`** (Family 02, deferred here since it composes Popover) — presentational (02.5): `suggestions` come from the caller, no `TanStack Query` dependency. Built on `cmdk` directly (not the generated `components/ui/command.tsx`, whose `CommandInput` hardcodes a `lucide-react` icon) + the raw `radix-ui` Popover for floating positioning. cmdk's `Input`/`List`/`Item` already implement the full ARIA combobox pattern out of the box (verified from its source) — nothing here hand-wires `role`/`aria-activedescendant`/etc. **Two known cmdk limitations**, both confirmed via source + real-browser testing rather than assumed, documented in full in `SearchField.tsx`'s doc comment: (1) `aria-expanded="true"` is hardcoded on the input regardless of whether the panel is actually showing; (2) `aria-activedescendant` only updates on a real arrow-key _move_ — the auto-highlighted first suggestion doesn't get it, so with exactly one suggestion (nowhere to move to) it never appears, even though `aria-selected`/`data-selected` and Enter-to-select all work correctly regardless.

## A known pitfall (read before adding a new variant)

The underlying generated primitives in `components/ui/` (e.g. `ButtonPrimitive`) always apply their **own default shadcn variant** internally (`bg-primary text-primary-foreground`) when you don't pass their `variant`/`size` props — which we deliberately don't, since we define our own variant vocabulary on top. Every wrapper variant here **must** include an explicit `bg-*` (or `bg-transparent`) class so `cn`/`tailwind-merge` actually cancels the primitive's default fill. A variant that has no visual fill (like `quiet`) needs `bg-transparent` explicitly — omitting it silently leaks the primitive's own navy background through. This was caught via real-browser computed-style inspection, not by unit tests (jsdom doesn't run a CSS engine) — see `tests/e2e/component-fixtures.spec.ts`, which regression-tests this exact class of bug.

## A related pitfall: conditional `data-[attr=value]:` variants vs. an unconditional class on the same property

Don't pair an **unconditional** base class (e.g. `border-border`) with a **conditional** Tailwind attribute variant on the _same CSS property_ (e.g. `data-[selected=true]:border-primary`) and assume the attribute match wins when true. Tailwind wraps variant selectors in `:where()` (zero added specificity), so that rule ties in specificity with the plain unconditional class and the tie is broken by stylesheet source order — which is not guaranteed to favor the variant, and did not in `Chip`'s original `filter` implementation (the selected cue silently never painted, confirmed via `getComputedStyle` in a real browser; jsdom would have shown the attribute was set correctly and given false confidence). The fix: make the conditional styling a **JS-level** ternary/`&&` appended after the base class in the same `cn(...)` call, so `tailwind-merge` fully drops the losing class from the DOM's `class` attribute instead of leaving both for CSS cascade order to referee — see `Chip.tsx`'s `SELECTED_FILTER_CLASSNAME`. This is the same fix shape as the `bg-*` leak above, just triggered by a same-specificity tie rather than a shadcn-primitive default.

## `lucide-react` is a real dependency, not a mistake

The `iconLibrary: "phosphor"` setting in `components.json` is **not honored** by this shadcn CLI version — generated `components/ui/*` primitives (Checkbox, Select, DropdownMenu, …) import their check/chevron/circle glyphs from `lucide-react` internally regardless. Since `components/ui/*` is never imported outside `components/foundation` (02.7 AD-2), this is an invisible implementation detail of the vendored layer — `@phosphor-icons/react` remains the only icon library used in anything hand-authored (foundation wrappers, features). `lucide-react` is installed as a real, necessary dependency for this reason; don't remove it assuming it's unused.

## Testing

Component tests (`*.test.tsx`, co-located) cover behavior, accessible names, and `jest-axe` violations — but **cannot** verify actual rendered CSS (jsdom has no real style engine) or full keyboard-interaction fidelity for complex Radix primitives (jsdom's Pointer/Focus Events implementation is incomplete). Anything about _actual computed styles_ or _real interaction behavior_ is verified in `app/test-fixtures/component-preview/` + `tests/e2e/component-fixtures.spec.ts` (Playwright, real browser, dedicated port 4300 — see that config's comment on why not 3000). Add a fixture entry + assertion there for any new variant that changes a color/fill, or any new keyboard interaction you're not fully confident jsdom is faithfully reproducing. `playwright.config.ts`'s `webServer.timeout` is `300_000` (was `120_000`) — a clean `next build` alone now takes ~90–160s with the Family 06/07 additions (Radix Tooltip/Dialog/Popover/cmdk); bump it again with headroom, don't re-tune to the minimum every time the build grows.

`tests/setup/vitest-setup.ts` polyfills `hasPointerCapture`/`setPointerCapture`/`releasePointerCapture`/`scrollIntoView` — jsdom doesn't implement these and every Radix-based interactive primitive (Select, RadioGroup, DropdownMenu, …) needs them. Without the polyfill, tests throw `TypeError: target.hasPointerCapture is not a function`, not a clean assertion failure. It also polyfills `ResizeObserver` (jsdom has no layout engine) — Radix Tooltip's arrow sizing and cmdk's `CommandList` both call it on mount (Family 06).

`vitest.config.ts`'s `testTimeout` is `10000`, not the 5000ms default: at the current suite size (130+ tests, real `userEvent` + Radix effects), a handful of click/focus-then-`findBy` tests intermittently exceeded 5000ms only when the _full_ suite runs together under load — never in isolation, and which specific test(s) hit it rotated run-to-run (Dialog/Drawer/DropdownMenu one run, Tooltip/Popover the next). Resource contention, not a component defect — verified by re-running the exact same failing tests alone (instant pass) and by seeing an entirely different, unrelated file (`DropdownMenu.test.tsx`, untouched that session) fail the same way in a different run.

Every Family 01–03 component that has real CSS/interaction risk now has a matching Playwright block in `tests/e2e/component-fixtures.spec.ts` (Button, RadioGroup, Input, FormField, Textarea, Checkbox, Switch, Select, DropdownMenu). `FormField`'s pure ARIA wiring, and `HelperText`/`ValidationMessage`'s plain text rendering, are deliberately **not** duplicated there — they're attribute/DOM checks with no computed-style or complex-interaction dependency, and jsdom already verifies them reliably; adding a browser test would be a redundant assertion, not a more confident one.

**Family 05 follows the same risk-based rule, not a per-family default.** Coverage is decided by implementation risk (does the component cancel a shadcn primitive default, or gate a style behind a conditional CSS selector — the two classes of bug this suite already exists to catch — or does it rely on real layout/paint?), not by which numbered Family a component belongs to:

- **`Badge`** — same "cancel the shadcn primitive's default fill" risk as `Button`'s `quiet` variant (see the pitfall above); covered — every variant's computed `background-color` is asserted mutually distinct.
- **`Card`** — same risk twice over: it cancels the generated `Card` primitive's `rounded-xl`/`shadow-sm` defaults (the Button-class leak), and `selectable`'s selected cue is a `data-[selected=true]:` conditional (the pitfall documented above, actually caught here — see Defects below); covered — rest-state radius/shadow, hover-lift shadow change, `asChild`'s real anchor, and selected-vs-unselected border color are all asserted.
- **`Chip`** — no shadcn primitive to leak from, but `filter`'s selected cue is the same `data-[attr]:` conditional-vs-unconditional-class risk as `Card`/`Checkbox`; covered — selected vs. unselected border color asserted after a real click.
- **`Table`** — `numeric`/`unavailable`/sort are purely additive Tailwind classes with no competing unconditional class on the same property (no cancellation risk), and `aria-sort`/conditional-caret rendering are plain attribute/DOM checks jsdom already verifies reliably in `Table.test.tsx`. **Not** given a Playwright block — there's nothing here jsdom can't already confirm, and a computed-style test would be redundant coverage, not a real regression guard.
- **`Avatar`** — thin wrapper around an already-token-bound generated primitive (no override/cancellation logic of its own); `name`→initials and the mandatory `aria-label` are plain string logic, fully covered by `Avatar.test.tsx`. **Not** given a Playwright block for the same reason as `Table`.

**Defect found via this pass:** `Chip`'s `filter` selected cue originally used a `data-[selected=true]:border-primary` CSS variant on top of an unconditional `border-border` base class — the exact specificity-tie failure mode documented in the pitfall above. It was caught here (real-browser `getComputedStyle` showed the border never changed on selection, despite `aria-pressed`/`data-selected` being wired correctly) and fixed by moving the selected styling to a JS-level conditional inside `cn(...)` (see `Chip.tsx`), the same fix shape as the primitive-default leak. No API or visual-design change — the fix only makes the already-documented selected cue actually render.

**Family 07:** `Progress` composes the raw `radix-ui` Progress primitive and hand-renders the indicator — determinate width (a real layout fact from `style.width`) and the indeterminate `@keyframes` sweep are both covered. `Skeleton`/`Loader`/`Banner` are **not** given a Playwright block: none cancels a shadcn primitive default, none gates a style behind a conditional CSS selector, and none depends on real layout/paint beyond Tailwind's own `animate-pulse`/`animate-spin` (already relied on, untested-in-Playwright, by Button's/IconButton's existing inline spinner) — confirmed by direct inspection that all four `Banner` tones already render mutually distinct computed backgrounds via a single JS-selected class (the same safe, no-conflict shape as `Chip` post-fix), so a dedicated test here would be redundant coverage, not a regression guard.

**Test-synchronization defect found via this pass (not a component defect):** `Progress`'s determinate-width test read two nested locators' `getBoundingClientRect()` concurrently via `Promise.all` immediately after `page.goto()` — the exact `locator.boundingBox()`-doesn't-auto-wait-for-layout pitfall documented two sections up (originally found for Switch's knob position). Direct, repeated inspection of the rendered component (outside Playwright's own timing) showed the fill width is perfectly stable and proportional on every read — the component was never wrong. Under the suite's parallel-worker load the race made both reads land on a stale `(0,0)` rect ~90% of the time (`--repeat-each=8`: 7/8 failed before the fix). Fixed by reusing the same established pattern: sequential reads, each after an explicit `waitFor({ state: "visible" })`, instead of a concurrent `Promise.all` right after navigation. Re-ran `--repeat-each=10` (20 runs) after the fix with zero failures.

**Family 06 + SearchField:** `Tooltip`, `Dialog`, and `Drawer` all compose a raw Radix primitive directly (real cancellation/behavior risk, the `Button`/`Card`-class of concern) — covered: Tooltip's focus-open (see the real defect below), Dialog's scrim color/radius + Tab-containment, Drawer's modal-vs-non-modal outside-pointer behavior. `Popover` is mostly a re-export; only its `z-50`→`--z-overlay` override is covered (a real stacking-context fact — it would render behind `--z-nav` if left at the shadcn default). `SearchField` combines cmdk's real keyboard-driven state with a Popover portal — covered: suggestions render in a correctly-anchored floating panel, ArrowDown updates `aria-activedescendant` (tested with 2+ suggestions specifically — see the cmdk limitation above for why not 1), Enter selects.

**Real defect found via this pass:** `Tooltip` never opened on keyboard focus — confirmed 100% reproducible (0/6 across fresh page loads) against a full production build, not a dev-mode fluke. Root-caused by tracing Radix's own source (not guessed): `TooltipContent` subscribes to a document-level `"tooltip.open"` event for cross-instance mutual exclusion inside a mount effect; on the synchronous focus path, that effect's mount and the dispatch from opening race within the same commit, so Content catches its own just-fired open event and immediately closes itself. Hover never raced this way because it opens via a real `setTimeout`, not synchronously inside the triggering event. Fixed with `forceMount` on `Tooltip`'s `Portal`/`Content` (mounts Content once, up front, rather than exactly when it needs to appear) plus explicit `data-[state=closed]:opacity-0 pointer-events-none` to hide it at rest, since `forceMount` means Presence no longer removes it from the DOM when closed. Verified the fix directly (6/6 opens on focus after, hover still 6/6, and confirmed no "ghost tooltip" visible before any interaction) before writing it up as a passing Playwright test.

**Two test-design mistakes caught re-running this pass (not component defects, but worth knowing before writing the next Family 06 test):**

- Asserting `.not.toBeVisible()` on the tooltip after Escape failed even though it _was_ correctly closed (`data-state="closed"`, `opacity: 0`) — `expect(locator).toBeVisible()` doesn't check `opacity`, only `display`/`visibility`. Any element hidden via `forceMount` + opacity (not DOM removal) needs an explicit computed-style check instead.
- Asserting a non-modal `Drawer` lets Tab "escape" it failed — traced via Radix's source and confirmed this isn't something `modal={false}` actually provides (`FocusScope`'s `loop: true` is hardcoded for Dialog-based content either way, so Tab always cycles within an open drawer). Rewrote the test around what `modal` genuinely controls: `disableOutsidePointerEvents` (confirmed directly — a real click on another button times out while a modal drawer is open, succeeds while a non-modal one is open).

Two more Playwright pitfalls worth knowing before writing the next test here:

- **`:focus-visible` and `.focus()` don't mix.** A script-triggered `locator.focus()` doesn't reliably match `:focus-visible` the way a real interaction does. Click directly into text-like controls instead (browsers special-case editable widgets to show focus-visible even on pointer focus); for non-editable controls, get there via a real `Tab`/click sequence.
- **`locator.boundingBox()` does not auto-wait for layout** the way `.click()`/`.fill()` do, and intermittently returned `null`/a stale `(0,0)` rect for a nested locator read immediately after `page.goto()` inside a `Promise.all`. `locator.evaluate(el => el.getBoundingClientRect())` waits for the element to attach and was reliable; when several such reads matter together (e.g. comparing two elements' geometry), do them sequentially after an explicit `waitFor({ state: "visible" })` rather than firing them all through `Promise.all` right after navigation.
